# Codex в проекте 1С

Перед работой прочитайте [общий регламент](PROJECT.md). В нём указаны параметры EDT, ветки, доступные проверки и правила BSL. В самом репозитории шаблона плейсхолдеры предназначены для производных проектов. Для правок самого шаблона учитывайте [правила участия](CONTRIBUTING.md).

Для поиска используйте `rg` и `rg --files`. Перед правкой прочитайте файл. Навыки Codex находятся в [.agents/skills](.agents/skills/), общие процедуры и скрипты - в [.claude/skills](.claude/skills/). Обозначение `/stage` и аналогичные команды в общих документах означают соответствующий навык. В Codex его можно вызвать как `$stage`. Профили этапа находятся в [.codex/agents](.codex/agents/), порядок передачи контекста - в [правилах выбора модели](docs/model-selection.md).

## Независимое ревью

На просьбу проверить ветку, коммит, этап или рабочее дерево работайте только на чтение. До просмотра диффа выпишите ожидаемый результат из спеки и плана проверяемой версии либо из карточки и решений владельца.

| Что проверяем | Граница |
| --- | --- |
| Ветка | От общей базы с веткой разработки из PROJECT.md до вершины выбранной ветки (`git diff <ветка-разработки>...<ветка>`) |
| Коммит или диапазон | `git show <коммит>` или `git diff <база> <конец>` по указанным ревизиям |
| Рабочее дерево | `git diff HEAD` для индекса и незаписанных изменений. Новые файлы найдите через `git status --short --untracked-files=all` и прочитайте отдельно |

Сверьте изменённое поведение с критериями приёмки, тесты - со спекой. Для BSL примените [чек-лист ревью](docs/bsl-code-review.md). Команда `python3 tools/diff-check/diff-check.py --база <коммит>` сравнивает базу с рабочим деревом. При ревью ревизий запускайте её в чистой копии конечной ревизии. Для формы используйте `python3 tools/form-audit/form-audit.py --src <каталог-src> --форма <путь-от-src>`. Если доступны только Git-объекты, проверьте дифф по Git и укажите пропуск проверок, которым нужна рабочая копия.

Диагностика EDT относится к открытому в EDT проекту, тесты - к версии в базе. Применяйте результаты к ревью после сверки пути и ревизии. Обновление базы и действия с записью выполняет уполномоченный участник вне независимого ревью.

В отчёте укажите границы и базу, вердикт «принять» или «доработать», результат сверки со спекой, выполненные проверки и причины пропусков. Для каждой блокирующей находки (Б1, Б2) дайте файл и строку, нарушенный критерий, правило или воспроизводимый сценарий и предложите исправление. Неблокирующие замечания (Н1, Н2) перечислите отдельно.
