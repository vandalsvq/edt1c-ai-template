# CLAUDE.md

Руководство для работы Claude Code над проектом 1С:Предприятие в EDT. Здесь - правила, которые
нарушаются молча, и маршрут к остальному. Состав объектов, процессы и памятки живут в `docs/`
и правятся там тем же коммитом, что и код; в этом файле не описывается состояние работ.
Когда таблицы раздела «Структура» разрастаются, их место - архитектурный документ проекта
(`docs/<prefix>-architecture.md`), а здесь остаётся ссылка.

> Это **шаблон**. Перед началом работы заполните разделы со знаком `<...>` под свой проект и удалите этот блок-предупреждение.

## Инструменты

**MCP-сервер: `<EDT-MCP / codepilot1c>`** - параметр проекта. Основной - **EDT-MCP**
([DitriXNew/EDT-MCP](https://github.com/DitriXNew/EDT-MCP), имя сервера `edtmcp`): плагин 1C:EDT,
работает через API EDT. Справочник - установка, согласие, карта задач, ловушки:
[`docs/edt-mcp-reference.md`](docs/edt-mcp-reference.md); подробности по инструменту отдаёт сам
сервер - `get_tool_guide(toolName)`. EDT-MCP поддерживает только EDT 2026.1 и 2026.2; проект на
более старой EDT работает с **codepilot1c**: тогда этот раздел заменяется разделом
«Инструменты» из [`docs/codepilot1c-reference.md`](docs/codepilot1c-reference.md) («Раздел
для CLAUDE.md»), а вызовы EDT-MCP в ролях цикла этапа и документах переводятся по его таблице
«Соответствие EDT-MCP». Подключение - `.mcp.json` по образцу
[`.mcp.json.example`](.mcp.json.example) (сам `.mcp.json` машинно-специфичен и в `.gitignore`)
или `claude mcp add --transport http -s local edtmcp http://127.0.0.1:<порт>/mcp`.

**Правила выбора:**

- **Поиск по паттерну** (методы, вызовы, вхождения) → `Grep` / `Glob` - в первую очередь, экономнее MCP на порядок
- **Готовый метод вместо нового кода** → перед любым нетривиальным алгоритмом или хелпером - справочник модулей проекта в `docs/` (если ведётся) и [`docs/bsp-common-modules.md`](docs/bsp-common-modules.md); `Grep` по исходникам - запасной путь. Нашёлся метод, которого нет в справочнике, - дописать справочник
- **Типизация, анализ логики, метаданные, формы, СКД** → инструменты `edtmcp`
- **Кто вызывает метод** → `get_method_call_hierarchy` (`direction="callers"`, `modulePath` от `src/`), `Grep` - запасной вариант
- **Текст запроса 1С перед вставкой в код или СКД** → `validate_query` (`dcsMode=true` для СКД)
- **Формы** - только инструментами, включая формы расширения: `create_metadata` на адрес члена формы, `modify_metadata` на свойства, `get_metadata_details(full=true)` - структура, `validate_form_model` - проверка; кнопка в командной панели - `parent="AutoCommandBar"` / `"<Таблица>.AutoCommandBar"`. Порядок сборки - справочник, раздел 5
- **СКД: варианты настроек, группировки, отборы, условное оформление** → навыки `skd-*`; простые правки наборов и параметров закрывает и `dcs`
- **Макет с именованными областями, объединениями, наборами колонок** → навыки `mxl-*`
- **Правка BSL** → `Read`, затем `Edit` (основной путь); `write_module_source` - когда модуль создаётся или нужна проверка синтаксиса при записи
- **Сомнения в API встроенного типа** → skill `bsl-check` (обёртка над `shcntx_ru`) или `get_platform_documentation`
- **Непонятное поведение в рантайме** → отладчик MCP (`set_breakpoint` → `run_yaxunit_tests(debug=true)` или `launch` → `wait_for_break` → `get_variables` / `evaluate_expression` → `resume`), профилирование - `start_profiling`
- **После изменений** → `get_project_errors` с `projectName` и `objectFqns=[<объект>]`, ответ - по таблице ниже. Правка мимо EDT (`Edit`, скрипт, ручной `.form`) - сначала `revalidate_objects` по затронутым объектам

**Разрушительные операции** (`delete_metadata`, `rename_metadata_object`, `update_database`, `delete_project`, `infobase_sessions(terminate)`) - двухфазно: вызов без `confirm` показывает, что будет сделано, затем `confirm=true`. `evaluate_expression`, `set_variable`, завершение сеансов - только по прямому поручению. Инструмент `git` сервера не включается: git - через Bash по правилам веток.

**Диагностика пачкой: `<да / нет>`** - параметр проекта (`<время одного вызова get_project_errors, дата замера>`): при «да» несколько диагностик подряд - одной пачкой; при «нет» - строго по одному вызову. Как выбрать: замерить один вызов `get_project_errors` с `objectFqns` - секунды и меньше - «да»; десятки секунд (крупная конфигурация) - «нет». Независимо от параметра диагностика не идёт в одной пачке с тем, что меняет файлы или модель (`Edit`/`Write`, `create_metadata` / `modify_metadata` / `write_module_source`, `revalidate_objects`, `update_database`, `diff-check --исправить`): сначала правка отдельным ходом. Параметр переключает владелец.

**Ответ инструмента → действие.** Ответ читается по признакам, а не по итоговой строке: «чисто» и «не найдено» бывают ответом не на тот вопрос. Повтор того же вызова на том же состоянии ничего не добавляет - кроме случаев из таблицы. Подробности - справочник.

| Ответ или симптом | Действие |
| --- | --- |
| `get_project_errors` после правки мимо EDT - «чисто» или прежняя ошибка | модель ещё не перечитала файл: `revalidate_objects` по объекту, затем повтор |
| `get_project_errors`: адрес в `objectsNotFound` | ответ не про этот объект: адрес - английский FQN верхнего уровня (`DataProcessor.prj_Обработка`), проект - `projectName` |
| `get_project_errors` упал по таймауту или шёл дольше ~15 с | до конца прохода - по одному вызову; в отчёте назвать время вызова: повод владельцу переключить «Диагностика пачкой» на «нет» |
| ответ на запись (`create_metadata`, `modify_metadata`) с `markers` | замечания уже свежие - разобрать их, не ждать отдельной диагностики; «метод отсутствует в модуле формы» до записи модуля - ожидаемо |
| ответ с `localesMissing` | записан один язык из нескольких: второй - отдельным `modify_metadata` с `language` |
| «Project is building: stage ...» | EDT пересобирает проект (обычно после обновления базы): пауза 20-30 с и повтор, не сбой |
| `update_database` с проектом расширения - «Application not found» | база привязана к другому проекту: `projectName` того проекта, к которому она привязана, и `applicationId` из `get_applications` |
| `update_database`: `stateAfter: UPDATED`, а правки в базе нет | правка мимо EDT не была замечена: `revalidate_objects` по объектам и ещё один `update_database`; в сомнении - `.metadata/.log` |
| вызов изменяющего инструмента ушёл в таймаут | в EDT ждёт окно подтверждения (уровень согласия «Ask always»): операция не выполнена - сказать владельцу, справочник §1 |
| `get_variables` - «(вычисление локальных переменных)» | значения ещё не посчитаны: повторить вызов |
| `validate_form_model`: путь `Items.<Таблица>.CurrentData.*` «не реквизит» | ложное срабатывание: путь допустим в платформе |
| ошибка аргумента, незнакомый параметр | `get_tool_guide(toolName)` и повтор один раз; второй догадки об имени нет |
| пустой поиск, «not found» | «в модели не найдено», а не «нет»: сперва FQN и имя проекта, затем подтвердить `Grep` |
| сервер не отвечает, инструмента нет в сессии, вызов не разрешён | проверка не выполнена - так и писать («не выполнено: <причина>»), не «проверено»; что поднять - владельцу |

MCP-инструменты **deferred** - схема раскрывается через поиск инструментов по имени.
Сессия без правок кода - трекер, документы, разбор журналов, планирование - сервер `edtmcp`
отключает на сессию (`/mcp`): его схемы оплачиваются в каждом вызове ([`docs/stage-cycle.md`](docs/stage-cycle.md), раздел 10).

### Skill `bsl-check`

```text
/bsl-check Структура.Вставить        ✓ Найти метод с сигнатурой
/bsl-check -m Массив                 ✓ Все методы типа
/bsl-check -p Строка                 ✓ Все свойства типа
/bsl-check -s Удалить                ✓ Поиск по названию
/bsl-check Структура.Вставить --full ✓ Полный вывод со ссылками
```

Скрипт работает поверх локального справочника синтаксиса 1С из публичного репозитория [`vandalsvq/hbk_md`](https://github.com/vandalsvq/hbk_md). Чеклист первичной настройки - [`docs/bsl-check-setup.md`](docs/bsl-check-setup.md).

### Навыки `skd-*` и `mxl-*`

Девять навыков для схем компоновки и табличных документов через JSON DSL - анализ, генерация,
точечная правка, валидация. Взяты из [`cc-1c-skills`](https://github.com/Nikolay-Shirokov/cc-1c-skills) (MIT)
и адаптированы под EDT. Требуют `lxml`, платформа 1С не нужна.

**Обязательно знать перед использованием** ([`docs/skd-mxl-toolkit.md`](docs/skd-mxl-toolkit.md)):

- макет как объект метаданных заводится **только** через MCP или EDT - навык пишет лишь файл содержимого;
- `skd-compile` / `mxl-compile` пишут файл в кодировке EDT (без BOM, LF) - это локальная правка скриптов, при обновлении из апстрима её повторяют;
- `skd-edit` не отвергает неверный формат `-Value`, а молча создаёт мусор - работать в чистом дереве,
  после правки `skd-validate` / `mxl-validate` и диагностика EDT (`get_project_errors`), смотреть `git diff` глазами;
- `*-decompile` → `*-compile` не идемпотентен - для авторства нового по образцу, не для round-trip.

### Skill `sync-template` / `push-to-template`

Пара скиллов синхронизации с репозиторием-шаблоном [`edt1c-ai-template`](https://github.com/vandalsvq/edt1c-ai-template):

- `/sync-template [пути]` - **забрать** переносимые файлы (docs со стандартами, скиллы, шаблоны спек) из шаблона в проект: сверка diff по каждому файлу, автозамена нейтрального префикса `prj_` на префикс проекта из CLAUDE.md.
- `/push-to-template [пути]` - **поднять** правку стандарта из проекта обратно в шаблон с обратной генерализацией (префикс → `prj_`, чистка проектной специфики), коммит в ветке клона шаблона.

Правки стандартов рождаются в проекте, поэтому подъём наверх - такая же штатная операция, как забор. В самом репозитории шаблона оба не применяются.

### Skill `strict-module`

`/strict-module <модуль>` - провести модуль через зачистку под строгую типизацию: директива `// @strict-types`, докблоки с типами всем методам, диагностики EDT в ноль, найденные дефекты на обсуждение, результат отдельным коммитом. Границы работы (что входит, чего не делают заодно, чем меряется цена) - [`docs/bsl-refactoring.md`](docs/bsl-refactoring.md). К модулям, заимствованным из БСП, не применяется.

### Skill `stage`

`/stage` - провести этап плана задачи через **цикл этапа**: основная сессия - куратор (бриф, решения, коммит), форму этапа собирает субагент `stage-form-designer` (если этап трогает форму и инструменты форм доступны), код пишет свежий субагент `stage-executor`, тесты по спеке - `stage-tester` (если подключён YAxUnit), проверяет другой свежий субагент `stage-reviewer` (файлы не правит), один круг правок, затем коммит с бампом версии, запись в план, отчёт и стоп до ревью владельца. Для задач с двумя этапами кода и больше. Контракт цикла (роли, что блокирует, поводы остановки, форматы отчётов, бриф, замер) - [`docs/stage-cycle.md`](docs/stage-cycle.md), роли - [`.claude/agents/`](.claude/agents/).

### Skill `close-task`

`/close-task [<prefix>-<N>]` - ритуал закрытия задачи: preflight ветки и версий, сверка с таблицей «Синхронизация документации», финальный коммит, перенос спеки в `specs/done/`, остановка перед merge (мерж делает владелец), запись в историю релизов, комментарий в трекер. Трекер и пути настраиваются в таблице «Настройка под проект» внутри самого скилла.

### Skill `analyst-doc`

`/analyst-doc [<prefix>-<N>]` - документ для аналитика или тестировщика по сделанной задаче: что изменилось глазами пользователя и в каком порядке это проверять. Источник - `spec.md` и история ветки, результат - `analyst-doc.md` в каталоге спеки (едет в `specs/done/` вместе с ней), при необходимости PDF на печать через headless-браузер. Жанр отдельный: ни имён модулей, ни префиксов, ни текстов запросов - читатель в код не смотрит. Вызывается сам или из `close-task` (шаг 5).

## Соглашения по коду

- Язык кода и комментариев - **русский**
- Имена переменных, процедур, реквизитов - на русском
- Клиент-серверные модули именуются `*КлиентСервер`
- Строгая типизация (`// @strict-types`) включается во всех новых модулях
- Все новые объекты - с префиксом проекта (`<prefix>_`)
- **Цвета в формах: `<стилевые / значения>`** - параметр проекта. «Стилевые»: элементы стиля конфигурации, цвета палитры 8.5 или стилевые цвета платформы; `WebЦвета` и абсолютные `#RRGGBB` запрещены - так форма сама подстраивается под тёмную тему 8.5. «Значения»: `WebЦвета` и абсолютные цвета разрешены - для решения, которое ставится на произвольную конфигурацию (например, универсальное расширение), где нужных элементов стиля может не быть; готовность к тёмной теме тогда проверяется глазами. Выбирает владелец при инициализации проекта; правила форм ([`docs/bsl-form-design-8.3.md`](docs/bsl-form-design-8.3.md), раздел 9) ссылаются на параметр
- **Зона владельца.** Правки владельца в дизайнере EDT и коммиты «правка владельца» - намеренное решение, свежее спеки и плана: не откатывать и не переделывать их по тексту документа без вопроса. `<Опционально: что наполняет только владелец, например состав меню раздела - команду завести можно, разместить её в меню - его решение>`

### Ключевое, что нужно держать в голове

**Структура общего модуля** - строго в таком порядке:

1. `#Область ПрограммныйИнтерфейс` - экспортные, документированы
2. `#Область СлужебныйПрограммныйИнтерфейс` - экспортные для подсистемы
3. `#Область СлужебныеПроцедурыИФункции` - неэкспортные

**Запросы - только русскоязычный синтаксис** (`ВЫБРАТЬ`, `ЛЕВОЕ СОЕДИНЕНИЕ`, `СГРУППИРОВАТЬ ПО`), всегда псевдонимы через `КАК`, псевдоним таблицы ≠ имя поля, `ТекущаяДатаСеанса()` вместо `ТекущаяДата()`.

**Критические антипаттерны** (CRITICAL):

- Запрос в цикле
- Обращение к реквизитам через точку (`Ссылка.Реквизит`)
- Подзапрос в SELECT
- Фильтр виртуальной таблицы в `ГДЕ` вместо параметров ВТ

**Транзакции** - `НачатьТранзакцию()` строго **до** `Попытка`:

```bsl
НачатьТранзакцию();
Попытка
    // ...
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();
    ВызватьИсключение;
КонецПопытки;
```

**Сообщения и исключения:**

- Не `Сообщить()` → `ОбщегоНазначения.СообщитьПользователю()` / `ОбщегоНазначенияКлиент.СообщитьПользователю()`
- Исключения не глотать: логировать через `ЗаписьЖурналаРегистрации` и пробрасывать `ВызватьИсключение`

**Пользовательские тексты** - только через `НСтр("ru='Текст'")`, не голым строковым литералом (сообщения, предупреждения, заголовки, тексты вопросов). Пробелов в разметке нет: ни вокруг `=`, ни после `;`. Подстановки - платформенный `СтрШаблон` (не `СтроковыеФункцииКлиентСервер.ПодставитьПараметрыВСтроку` - метод устарел). Подробнее - [`docs/bsl-coding-standards.md`](docs/bsl-coding-standards.md).

**Вложенные вызовы** - вызов с параметрами в аргументе другого вызова выносится в локальную переменную, даже если внешний вызов помещается в одну строку: `Реестр = ПолныйРеестр(Окружение);`, затем `РазобратьРеестр(Реестр, ...)`. Коллекция `Для Каждого`: вызов с параметрами (кроме простых методов платформы) и цепочка вызовов - сначала в переменную, цикл по ней. В модулях тестов правило не проверяется. Исключения (`НСтр`, простые методы платформы над строками, числами и датами, вызовы без параметров, конструкторы `Новый`, вызов в аргументе `Вставить` и `Добавить` и др.) - разделы «Вложенные вызовы» и «Коллекция цикла» в [`docs/bsl-coding-standards.md`](docs/bsl-coding-standards.md); проверка - скриптом [`tools/nested-calls/nested-calls.pl`](tools/nested-calls/nested-calls.pl), а вместе с остальной механикой диффа - [`tools/diff-check/diff-check.py`](tools/diff-check/diff-check.py) одним проходом.

**Тире** - только дефис-минус `-` (U+002D), везде: код, литералы, комментарии, спеки, документация, сообщения коммитов и комментарии к задачам. Длинное (U+2014) и среднее (U+2013) запрещены. Проверка перед коммитом - [`tools/diff-check/diff-check.py`](tools/diff-check/diff-check.py) (`--индекс`) или команда из [`docs/bsl-coding-standards.md`](docs/bsl-coding-standards.md).

**Запросы выполняются в методе-исполнителе**, поля выборки перечислены в его `Возвращаемое значение`: строгая типизация состав полей из текста запроса не выводит - ни при динамическом тексте, ни при литерале целиком.

**Модули форм** ([`docs/bsl-form-module-rules.md`](docs/bsl-form-module-rules.md)):

- Реквизиты и методы платформы - через `ЭтотОбъект.` (в форме исключения - `Объект`, `Элементы`, `Команды`, `Параметры`; так же в модулях объекта и набора записей); методы, написанные в самом модуле, - без префикса; `ЭтаФорма` устарел
- Серверные методы (`&НаСервере`, `&НаСервереБезКонтекста`) обязаны оканчиваться на `НаСервере`
- Метод не использует контекст формы → `&НаСервереБезКонтекста`; чисто вычислительный над данными → `&НаКлиентеНаСервереБезКонтекста` с параметром `Форма`/`Объект`
- Не вызывать сервер в циклах
- Предупреждение без ожидания ответа - `ПоказатьПредупреждение` без обработчика, не `ПредупреждениеАсинх` ([`docs/bsl-async.md`](docs/bsl-async.md))

**Строгая типизация** ([`docs/bsl-strict-types.md`](docs/bsl-strict-types.md)): `// @strict-types` - первая строка новых модулей; параметры - `знач` (нижний регистр) по умолчанию, исключения - §3 того же документа; `Перем` без начального значения запрещён; смена типа переменной запрещена. Doc-блок с типами (`Параметры` / `Возвращаемое значение`) обязателен для **всех** методов, включая неэкспортные и обработчики событий. `//@skip-check` и другие подавления замечаний EDT не ставить самому - ни по памяти, ни по образцу соседнего кода: объяснить владельцу, что за проверка и почему её уместно подавить, и ставить только с его разрешения; иначе устранять причину.

**Форматирование:** однотипные блоки подряд (`=`, `Структура.Вставить`, инлайн-типы) выравнивать обязательно; добор до `=` - табами до общей табопозиции (мелкий добор 1-2 пробела - исключение), в серии вызовов - до запятой, а не после; псевдонимы `КАК` в запросах не выравниваются; отступы - табами.

**Малая правка не оправдывает компромиссный дизайн:** «минимальный дифф» - не довод за out-параметр, ложную декларацию или обход стандартов; сомнение между чистым и дешёвым вариантом - вопрос владельцу до кода ([`docs/bsl-refactoring.md`](docs/bsl-refactoring.md), «Принципы»).

### Публичные формулировки (СТРОГО)

`<Опционально - раздел нужен, если у проекта есть публичная витрина (репозиторий, сайт, changelog).>`

Всё, что попадает в публичное пространство (issue, milestone, комментарии, коммиты, публичная документация, сайт), должно быть:

- **сдержанным и нейтральным** - без превосходных степеней, без «отказа от X», без острых формулировок;

## Ветки и коммиты

- Релизная ветка: `<пример: master / main>`
- Основная ветка разработки: `<пример: develop>`
- Рабочие ветки: `<пример: feature/<prefix>-<N>>` от ветки разработки
- **В ветку разработки - только мерж feature-ветки** (`--no-ff` или PR), без прямых коммитов, даже однострочной правки после закрытия задачи. Правка документов и правил вне текущей задачи - короткой веткой от свежей ветки разработки (удобно через `git worktree`, не трогая ветку задачи); черри-пик в ветку разработки - тот же прямой коммит
- **Перед слиянием feature-ветки - сначала забрать ветку разработки из origin** (`git fetch origin` + обновить локальную): при работе на нескольких машинах и в параллельных сессиях локальная ветка почти наверняка отстала, и слияние в устаревшую ветку молча теряет чужую работу
- Формат коммита - **короткий заголовок, рассказ в теле**: стартовый контекст сессии, `git log --oneline` и список коммитов на GitHub показывают только заголовок, поэтому в нём одна суть, а подробности - в теле
  - Заголовок - до ~72 символов: `<prefix>-<N> <что сделано>; <версия>`, у этапа - `<prefix>-<N> этап <имя>: <что>; <версия>`; версия - если поднималась. Номер задачи - текстом (`prj-42`), не `#N`: голый `#N` GitHub связывает с issue этого репозитория, а задача может жить в другом
  - Тело - через пустую строку: первой строкой ссылка на issue (`<URL issue>` - по ней трекер связывает коммит с задачей); дальше подробности списком, пункт на модуль или тему, без жёсткого переноса строк. Коммит без подробностей (архивация спеки) - тело из одной ссылки
  - Запись - `git commit -m "<заголовок>" -m "<ссылка>" -m "<подробности>"`: каждый `-m` - отдельный абзац
- PR открывается в ветку разработки, релиз - в релизную ветку
- **Состав коммита - решение владельца:** не исключать его правки по своей инициативе; при выборочном `git add` показать, что войдёт и что останется, и спросить, если состав неочевиден. При закрытии задачи чужие незакоммиченные правки в дереве - спросить о каждой, умолчание «в финальный коммит задачи»
- Не добавлять `Co-Authored-By` в сообщения коммитов
- После каждого значимого этапа работы - локальный коммит в feature-ветку; `git push` - только по явной просьбе владельца

**Версия конфигурации** - повышайте перед коммитом, затрагивающим каталог EDT-проекта. Файл: `<EDT-проект>/src/Configuration/Configuration.mdo`, атрибут `version`. Сегменты меняют только агент или владелец руками - платформа и обновление ИБ их не трогают: изменённый `version` в дереве - чья-то правка, смотреть дифф.

Соглашение об инкременте версии (пример):

- **Промежуточный коммит внутри задачи** - четвёртый сегмент +1 (`2026.1.4.0` → `2026.1.4.1`)
- **Коммит, закрывающий задачу** - третий сегмент +1, четвёртый в `0` (`2026.1.4.7` → `2026.1.5.0`)
- Закрывающий бамп делает автор финального содержательного коммита; не бампать задним числом отдельным шагом ритуала закрытия - если сегмент не поднят, спросить владельца
- Коммит только с файлами вне EDT-проекта (планы, спеки, docs) - версию не менять

**Версия модуля обработки** - `<опционально: если у обработок проекта есть собственный метод `Версия()`, опишите правило инкремента здесь; это отдельный контракт, не зависящий от версии конфигурации>`.

## Specification-Driven Development

Проект ведётся по методологии **SDD: значимое изменение начинается со спецификации**, а не с кода. Спека живёт в [`specs/`](specs/) и является источником истины для поведения.

- Процесс, именование, статусы: [`specs/README.md`](specs/README.md)
- Шаблоны: [`specs/_template/spec.md`](specs/_template/spec.md) (стабильный контракт) + [`specs/_template/plan.md`](specs/_template/plan.md) (этапы, решения - транзиентное)
- Ретроактивные спеки: [`specs/retro/`](specs/retro/)
- Черновые планы до спек (груминг бэклога, зонтичные инициативы, реестры): [`planning/`](planning/) - когда писать туда, а когда сразу в спеку, см. [`planning/README.md`](planning/README.md)

Активная спека - папка `specs/<prefix>-<N>/` с `spec.md` + `plan.md`. Задача с циклом этапа ведёт план четырьмя файлами - `plan.md`, `questions.md`, `decisions.md`, `log.md` (шаблон [`plan.md`](specs/_template/plan.md), «Файлы плана»); у задачи без цикла порог выделения `decisions.md` из `plan.md` - ~15+ записей в разделе «Решения».

**Когда спека обязательна:**

- Новая фича или изменение поведения, видимого пользователю
- Изменение публичного контракта: экспортные методы общих модулей, реквизиты ключевых обработок, XDTO-пакеты
- Изменение затрагивает несколько обработок/подсистем

**Когда спека не нужна:** опечатка, локальный багфикс без изменения контракта, рефакторинг без изменения поведения, обновление зависимостей и конфигов.

**Язык спек** - русский. **Исключение:** имена объектов публичного контракта сериализации (XDTO, типы интеграций) - на оригинальном языке (обычно английском).

2. Работа в ветке `feature/<prefix>-<N>` от ветки разработки. Перед началом проверить текущую ветку (`git branch --show-current`); при незакоммиченных изменениях в ветке разработки - спросить владельца (stash / commit / discard), не решать самому
3. Задача с двумя этапами кода и больше ведётся **циклом этапа**: основная сессия - куратор, форму этапа собирает субагент `stage-form-designer`, код пишет `stage-executor`, тесты по спеке - `stage-tester` (обе роли - по условиям контракта), проверяет субагент `stage-reviewer`, затем ревью владельца. Порядок - skill `/stage`, контракт - [`docs/stage-cycle.md`](docs/stage-cycle.md)
4. Перед изменениями - `Grep` для поиска, затем `Read` / `read_method_source` для контекста
5. Не нарушать архитектурные ограничения зависимостей
6. Метаданные и формы - инструментами MCP (`create_metadata` / `modify_metadata`), разрушительные - двухфазно (`confirm`)
7. Новый модуль объекта - `write_module_source`; правка существующего - `Edit`, затем `revalidate_objects`
8. После изменений - `get_project_errors` по затронутым объектам
9. Для нетривиальной логики - YAxUnit (когда подключится фреймворк). После правки кода, покрытого тестами, - прогон модулей затронутых объектов в рабочей базе ([`docs/yaxunit-bootstrap.md`](docs/yaxunit-bootstrap.md) §6.1); полный прогон - в тестовой базе
10. **Расхождение кода и `spec.md` - обновляется спека тем же PR.** Транзиентное (этапы, решения) - в `plan.md`
11. Коммитить атомарно с привязкой к issue и ссылкой на спеку
12. Закрытие задачи - skill `/close-task`: финальный коммит, документ для аналитика (`/analyst-doc`, если задача идёт на функциональное тестирование), перенос спеки в архив, остановка перед merge, комментарий в трекер
13. После merge и закрытия issue: статус `spec.md` → `done`, папка переносится в `specs/done/<prefix>-<N>/`. Ретро-спеки и `superseded` не переносятся
