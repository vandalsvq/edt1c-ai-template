# Specification-Driven Development

Этот каталог — источник истины для поведения проекта. Каждая значимая
фича или подсистема описывается спецификацией **до** того, как пишется
код. Спецификация живёт в git, ревьюится, обновляется вместе с кодом.

## Зачем

- Дизайн обсуждается в тексте, а не в коде — дешевле менять решение.
- Архитектурные ограничения проверяются на стадии спеки, а не на ревью PR.
- Claude и человек работают от одного документа — меньше расхождений
  между тем, что задумано, и тем, что попало в коммит.
- Подготовка к будущему автоматическому тестированию: критерии приёмки
  из спеки станут `.feature` (Vanessa) и YAxUnit-тестами, когда эти
  фреймворки будут подключены.

## Структура спеки

Активная спека на issue — это **папка** `specs/<prefix>-<N>/` с двумя файлами:

- [`spec.md`](_template/spec.md) — стабильный контракт: контекст,
  поведение, контракты, критерии приёмки. Переживает merge и уезжает
  в `specs/done/<prefix>-<N>/spec.md`.
- [`plan.md`](_template/plan.md) — транзиентный план + открытые
  вопросы + история решений. Живёт до закрытия задачи; после merge
  либо удаляется (если ценного контекста не осталось), либо уезжает
  в `specs/done/<prefix>-<N>/plan.md` как архив развития.

Такое разделение решает две проблемы одновременно:

- в ревью и в контексте ассистента не мешают уже пройденные этапы и
  журнал решений;
- после merge не приходится перечитывать сотни строк транзиентных
  заметок, чтобы вспомнить, что именно гарантирует фича.

**Порог выделения `decisions.md`:** если записей в разделе «Решения»
становится ~15+ — вынести их в соседний `decisions.md` рядом с
`plan.md`. Для типовой фичи (3–7 решений) — держать в хвосте `plan.md`.

Ретро-спеки остаются в одиночном формате — см. раздел
«Ретроактивное покрытие» ниже.

## Процесс

### Для новых фич

1. Появляется issue в трекере проекта.
2. Перед кодом — создаётся папка `specs/<prefix>-<N>/`, в неё копируются
   оба файла из `specs/_template/`. Статус в `spec.md` — `draft`.
3. Спека согласуется с владельцем (итеративно). Статус → `approved`.
4. Только после `approved` — ветка `feature/<prefix>-<N>` от ветки разработки, код.
   Статус спеки → `in-progress`.
5. Коммит ссылается на спеку и issue:
   `<URL issue> <описание>`.
6. При расхождении кода и `spec.md` — обновляется **спека**, не коммит
   задним числом. Обновление идёт тем же PR.
7. После merge и закрытия issue — статус → `done`, папка переносится
   в `specs/done/<prefix>-<N>/` (имя не меняется). При переносе решается
   судьба `plan.md`: либо остаётся как архив развития, либо удаляется.
   Ретро-спеки и `superseded` не переносятся.

### Для ретроактивного покрытия существующих подсистем

1. Берётся подсистема из приоритизированного списка.
2. Читается код, пишется спека без `issue` (поле `issue: retro`),
   описывающая **текущее** поведение как контракт.
3. Обнаруженные при этом несоответствия, баги, долги — фиксируются
   как отдельные issues и отдельные спеки на изменения.
4. Ретро-спеки живут в `specs/retro/` в виде одиночного файла
   `<подсистема>.md` — папочная структура `spec.md`/`plan.md` для них
   не используется (плана реализации нет, решения по текущему
   поведению фиксируются внутри одного документа).

## Правила языка

- Язык спек — **русский**.
- Бизнес-контекст, описание поведения, критерии приёмки, имена
  процедур BSL — на русском.
- **Исключение:** имена объектов публичного контракта сериализации
  (XDTO, имена полей внешних API) — на оригинальном языке. Это
  публичный контракт, переводить его нельзя.

## Правила именования файлов

- `specs/<prefix>-<N>/spec.md` + `specs/<prefix>-<N>/plan.md` — активная
  спека на issue (`draft` / `approved` / `in-progress`). Имя папки —
  `<prefix>-<N>` без описательной части; название живёт в поле `title`
  фронтматтера `spec.md`.
- `specs/<prefix>-<N>/decisions.md` — опционально, когда записей решений 15+.
- `specs/done/<prefix>-<N>/…` — завершённая спека (`done`), переносится
  сюда после merge и закрытия issue.
- `specs/retro/<подсистема>.md` — ретро-спека на подсистему одиночным
  файлом (не переносится в `done/`).
- `specs/_template/spec.md` + `specs/_template/plan.md` — шаблоны
  (не править, копировать).
- `specs/README.md` — этот файл.

## Статусы

| Статус | Значение |
| --- | --- |
| `draft` | Черновик, обсуждается |
| `approved` | Согласована, можно кодить |
| `in-progress` | Код в работе |
| `done` | Смержено в основную ветку разработки, issue закрыт; папка лежит в `specs/done/<prefix>-<N>/` (для спек старого одиночного формата — файл в `specs/done/`) |
| `superseded` | Заменена другой спекой (указать какой); остаётся рядом с заменяющей |

## Приоритет ретроактивного покрытия

Порядок имеет значение — идти от самого простого и изолированного к
самому сложному:

1. **Ядро / базовые утилиты** — изолированная библиотека, внешних
   зависимостей нет. Лучшая точка входа: понятный скоуп, легко описать
   контракты.
2. **Клиент-серверные общие модули** — фундамент объектной модели.
3. **Публичные контракты сериализации** (XDTO-пакеты) — формализуем как есть.
4. **Главные модули объектной модели** — структура часто уже отражена в XDTO.
5. **Слой исполнения / рендеринга** — зависит только от ядра.
6. **Специализированные обработчики** (форматы вывода, интеграции).

Дальше — по мере необходимости.
