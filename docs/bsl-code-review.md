# Чеклист ревью BSL-кода

Применяется при ревью кода 1С (*.bsl).

---

## Границы ревью

**Ревьюится только изменённая часть.** Прогонять чек-лист по файлу целиком нельзя:
в старых обработках и модулях замечаний наберётся столько, что содержательные
утонут, а объём правок выйдет за границы задачи. Точка отсчёта - дифф ветки
(`git diff <ветка разработки>...HEAD`, в цикле этапа - от базового коммита этапа), а не
текущее состояние файлов.

Исключение - код, поведение которого меняется из-за правки: он попадает в разбор
именно как затронутый, а не «заодно, раз уж открыли файл».

Замечание к неизменённому коду не пропадает: оно уходит строкой в `plan.md`
задачи или отдельной задачей, но не правится в текущей.

## Классификация находок

### Critical - блокировать коммит

- Синтаксические ошибки
- SQL injection (конкатенация строк в запросе вместо параметров `&Параметр`)
- Риск порчи данных
- Пробои безопасности (hardcoded пароли, обход RLS)
- Операции, заведомо выполняющиеся >10 секунд без оптимизации
- Нарушения БСП с breaking changes

### High - исправить до merge

- Логические ошибки
- Отсутствие обработки ошибок (пустой блок `Исключение`)
- N+1 запросы (запрос в цикле)
- Отсутствие индексов на фильтруемых полях
- Недостаточный контроль доступа (нет проверки прав)
- Дублирование кода >50 строк
- Цикломатическая сложность >15

### Medium - исправить в спринте

- Нарушение конвенций именования
- Отсутствие документации экспортных функций
- Субоптимальные алгоритмы
- God-модуль, длинные функции >200 строк
- Незначительные отклонения от БСП
- Проблемы с тестируемостью

### Low - технический долг

- Форматирование
- Стиль комментариев
- Именование переменных
- Мелкие оптимизации
- Возможности для рефакторинга

## Шкала уверенности

| Баллы | Уровень | Описание |
|---|---|---|
| 0-25 | Низкая | Возможно false positive |
| 26-50 | Средняя | Стоит обсудить |
| 51-75 | Высокая | Вероятная реальная проблема |
| 76-100 | Очень высокая | Подтверждённая проблема с доказательствами |

Репортить: при ревью кода - только ≥75, при ревью архитектуры - ≥50.

## Security-паттерны 1С

### Уязвимости - искать

- **SQL injection**: конкатенация строк в `Запрос.Текст` вместо `&Параметр`
- **XSS**: неэкранированный вывод пользовательских данных в формах
- **Обход RLS**: отсутствие проверок `ПравоДоступа()` / `РольДоступна()`
- **Hardcoded секреты**: пароли, токены, ключи API прямо в коде
- **Небезопасная обработка данных**: внешние данные без валидации

### Best practices

- Параметризованные запросы (`&Параметр`, не конкатенация)
- Валидация всех внешних входов
- Проверка прав перед операциями:
  ```bsl
  ПравоДоступа("Изменение", Метаданные.Справочники.Клиенты)
  ```
- Секреты - в безопасном хранилище, не в коде

## Формат отчёта ревью

```
Файл: путь/к/модулю.bsl
Статус: PASS | FAIL | NEEDS_WORK
Critical: N, High: N, Medium: N, Low: N

[SEVERITY] Строка XX: Краткое описание
  Проблема: что не так
  Код: фрагмент проблемного кода
  Исправление: как исправить
  Пример: правильный код
  Влияние: на что влияет
```

## Быстрый чеклист перед merge

- [ ] Нет запросов в цикле
- [ ] Нет обращений к реквизитам через точку у ссылочных типов
- [ ] `НачатьТранзакцию()` - строго до `Попытка`
- [ ] Исключения логируются и пробрасываются (не глотаются)
- [ ] Нет `Сообщить()` - использованы методы БСП
- [ ] Пользовательские тексты - через `НСтр`, не голым литералом
- [ ] Нет конкатенации строк в запросах вместо параметров
- [ ] Нет hardcoded паролей/токенов
- [ ] В модулях с контекстом (форма, объект, набор записей) данные и методы платформы - через `ЭтотОбъект.` (в форме кроме `Объект`, `Элементы`, `Команды`, `Параметры`); методы, написанные в самом модуле, - без префикса
- [ ] Серверные методы формы оканчиваются на `НаСервере`; без нужды в контексте - `&НаСервереБезКонтекста`
- [ ] Экспортные функции задокументированы; в модулях `// @strict-types` - все методы (вкл. неэкспортные и обработчики)
- [ ] Новое поле структуры (`Вставить`) описано строкой `* Поле - Тип - описание` в докблоке её конструктора
- [ ] Метод другого модуля, который теперь вызывается, объявлен с `Экспорт`: диагностика `scope=module` вызов приватного метода из другого модуля не ловит, нужна `scope=project`. Делать метод публичным не хочется - экспортная обёртка
- [ ] Новых `//@skip-check` и других подавлений нет, кроме согласованных с владельцем
- [ ] Комментарии в коде - причина, без номеров задач, параграфов спеки и дат прогонов (кроме шапки тестового модуля)
- [ ] Новые имена (идентификаторы, области, синонимы, комментарии) - прямой смысл, без метафор и жаргона из обсуждений («Прямой смысл, а не метафора и не жаргон» в `bsl-coding-standards.md`)
- [ ] `знач` в нижнем регистре; параметры объявлены `знач` по умолчанию (исключения - [`bsl-strict-types.md`](bsl-strict-types.md) §3)
- [ ] У методов, вызываемых с клиента на сервер («Вызов сервера», `&НаСервере*`), заполняемые параметры не помечены `знач` - иначе результат на клиент не вернётся; лучше возвращать результат функцией
- [ ] Обработчики, назначенные `УстановитьДействие`, названы с `Подключаемый_`
- [ ] Однотипные блоки выровнены табами (`=`, аргументы `Вставить`, инлайн-типы); добор до запятой, не после; в doc-комментариях отступ и колонка типов - тоже табами
- [ ] Вызов с параметрами в аргументе другого вызова вынесен в локальную переменную, в том числе в однострочном вызове; вызов с параметрами и цепочка вызовов в заголовке `Для Каждого` - тоже (исключения - «Вложенные вызовы» и «Коллекция цикла» в `bsl-coding-standards.md`; модули тестов правило не проверяет). Глазом вложенность пропускается, а регулярка тонет в ложных срабатываниях на `СтрШаблон(НСтр(...))` и не видит заголовок цикла - отдельный проход скриптом [`nested-calls.pl`](../tools/nested-calls/nested-calls.pl), он знает исключения правила: по диффу `git diff -U0 <база> -- <Каталог.Имя> | perl tools/nested-calls/nested-calls.pl --diff` (из корня репозитория; путь отсекает модули тестов и `tools/nested-calls/cases.bsl` - набор примеров с намеренными нарушениями), по модулю целиком - `perl tools/nested-calls/nested-calls.pl <модуль>`. Строка переносится, только если длиннее 120 символов - считать символы, а не байты (`awk` на macOS считает байты кириллицы)
- [ ] Результат условия присваивается в скобках: `Выполнено = (КодВозврата = 0)`
- [ ] В тексте запроса псевдонимы `КАК` не выровнены - перед `КАК` ровно один пробел
- [ ] Запрос выполняется в методе-исполнителе, поля выборки перечислены в его `Возвращаемое значение`
- [ ] Длинного и среднего тире нет нигде - ни в коде, ни в текстах, ни в сообщении коммита
- [ ] Область с более чем 10 методами разбита на подобласти по назначению; имён-заглушек (`Прочее`, `Вспомогательные`) нет
- [ ] В служебных областях форм и команд методы упорядочены по директиве (`&НаКлиенте` → `&НаКлиентеНаСервереБезКонтекста` → `&НаСервереБезКонтекста` → `&НаСервере`), процедуры выше функций, связанные методы не разорваны
- [ ] Представления ошибки взяты из `ОбработкаОшибок`, не глобальные
- [ ] Соблюдены архитектурные ограничения зависимостей (см. [`../CLAUDE.md`](../CLAUDE.md) → Архитектурные ограничения)
- [ ] Версия конфигурации повышена (перед коммитом)
- [ ] `get_diagnostics` не показывает новых ошибок (не `edt_diagnostics`: у него обязателен
      `command`, а `metadata_smoke` создаёт мусорные объекты метаданных в рабочей конфигурации)
- [ ] Дифф чистый - раздел ниже

## Гигиена диффа перед коммитом

Ни EDT, ни сборка на эти дефекты не ругаются, поэтому они проверяются скриптом, а не глазами.

- **Кодировка.** Норма проекта - UTF-8 без BOM. Скрипт, который читает и пишет файл с
  перекодированием (например, через `utf-8-sig`), может добавить BOM файлу, у которого его не
  было: скрипт читает первые три байта и пишет файл с тем же состоянием BOM. Подмена кодировки
  в `git diff --cached | grep "^[+-]" | cat -e` видна как правка первой строки.
- **Переводы строк.** В репозитории файлы в LF. Если рабочее дерево на Windows в CRLF, запись
  скриптом без сохранения переводов строк переписывает файл целиком - правка одной строки
  становится диффом на весь файл. Признак - число строк в `git diff --stat` намного больше,
  чем в `git diff --ignore-cr-at-eol --stat`. Git Bash `\r` в выводе прячет - считать переводы
  строк Perl-ом.
- **Двойные пустые строки.** Скриптовое удаление и перестановка методов оставляют `\n\n\n`
  между методами и пустую строку сразу после `#Область ...` - приводить к одной пустой строке
  между методами и к нулю после строки области.
- **Таб в пустых строках.** Пустая строка внутри тела метода в модулях 1С обычно `\t`, а
  Edit пишет пустые строки замены без таба: дифф пухнет парами `-\t` / `+`. Проверка -
  `git diff -U0 | grep '^[-+][[:space:]]*$' | cat -et | sort | uniq -c`. Лечение - выровнять
  новый файл с `git show HEAD:<файл>` по строкам без хвостовых пробелов
  (`difflib.SequenceMatcher`), совпавшим пустым строкам вернуть исходный текст, вставленным
  внутри тела метода поставить `\t`. Не ставить таб всем пустым строкам подряд: в исходниках
  встречаются и пустые без таба. Сколько табов в пустой строке, зависит от модуля (в одних -
  один при любой вложенности, в других - по вложенности): посчитать по модулю до правки.
- **Применилось всё задуманное.** Если пакетная правка (код плюс докблок) не применилась и её
  сузили до кода, вторая половина - обязательный следующий шаг, а не забытый хвост.
- **Переименование.** Порядок - правка → `git add` → `git mv` (или сначала `git mv`, потом
  правка). Если файл поправлен, не добавлен в индекс и переименован, коммит выходит «rename
  100%» без правки. После такого коммита сверить `git show HEAD:<новый путь>`.
