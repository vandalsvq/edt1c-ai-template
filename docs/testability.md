# Проверяемость и автономные прогоны

Правило проектирования: **способ проверки закладывается в спеку вместе с фичей**,
а не придумывается после реализации. Если проверка требует владельца в роли
оператора интерактивного цикла («запусти форму, вставь текст, нажми кнопку,
верни результат») — это дефект проектирования: в область изменений задачи
закладывается обвязка автономного прогона.

Происхождение правила: итерации качества сквозного сценария гонялись
через владельца вручную на стенде «Диагностика» — десятки однотипных циклов,
которые платформа умеет выполнять сама через запуск с параметрами командной
строки. Реализация обвязки описывается в спеке задачи.

## Правило при написании спеки

1. Каждый критерий приёмки (§5 шаблона `spec.md`) помечается способом проверки
   из лестницы ниже.
2. Обвязка (лончер, сценарий, формат результата) — часть области изменений (§2)
   и оценки трудоёмкости. Переиспользуемая обвязка может выделяться в отдельную
   dev-задачу, но тогда зависимость фиксируется в спеке явно.
3. Ручная проверка владельцем — допустимый **остаток**, а не способ по умолчанию:
   в спеке явно перечисляется, что именно смотрит владелец и почему это дешевле
   автоматизации (визуальная оценка вёрстки, единичный смоук, UX-впечатление).

Триггеры, при любом из которых обвязка **обязательна**:

- проверка — интерактивный цикл через владельца более чем на пару итераций;
- поведение недетерминированное (LLM, внешние сервисы) и вывод нужно оценивать
  серией прогонов, а не единичным запуском;
- есть контрольный набор / полигон и нужен замер метрик или регресс
  (пример: `tests/assistant-quality/`);
- задача предполагает повторяющиеся итерации настройки (промпты, ранжирование,
  веса) — каждая итерация без обвязки стоит один цикл ручного теста.

## Лестница способов проверки

От дешёвого к дорогому; выбирать самый дешёвый, который реально проверяет
критерий.

| # | Способ | Что проверяет | Когда применять |
| --- | --- | --- | --- |
| 1 | `edt_diagnostics` + статика | Компилируемость, типизация, стандарты | Всегда, после любых изменений |
| 2 | YAxUnit (`author_yaxunit_tests`) | Детерминированная логика без сети и LLM | Когда фреймворк подключён; юниты на чистые функции |
| 3 | Отладчик MCP (`set_breakpoint` → `evaluate_expression`) | Точечное поведение в рантайме | Разовая проверка гипотезы, не регресс |
| 4 | **Headless-прогон (лончер)** | Сквозные прогоны любых программных механизмов: петля ассистента, объектная модель схемы, исполнитель, печать, файлы; серии и метрики | Недетерминированный вывод, контрольные наборы, интеграция, эталоны |
| 5 | Vanessa Automation | UI E2E | Когда каркас подключён и сценарий про интерфейс |
| 6 | Владелец вручную | Визуальная оценка, UX | Только остаток, перечисленный в спеке явно |

Headless-прогон — **дополнение** к YAxUnit, не замена: юниты остаются быстрым
детерминированным слоем без внешних вызовов, лончер закрывает то, что юнитами
не проверяется в принципе. Для детерминированной логики (схема, исполнитель)
при подключённом YAxUnit предпочтительнее юниты; ниша headless-прогона там —
сценарии с файлами, эталонами рендеринга, клиентским контекстом или сетью.

## Паттерн headless-прогона

**Контракт** проектируется отдельно от транспорта: `сценарий (JSON) →
прогон → результат (JSON)`. Механизм универсальный: сценарий объявляет
**вид прогона** — петля ассистента, объектная модель схемы, рендеринг
исполнителем, сериализация XDTO и другие программные механизмы, — а лончер
диспетчеризует по виду. Конверт формата един (вид прогона + параметры +
элементы со стабильными `id`, русские ключи), состав элементов зависит от
вида; образец для вида «ассистент» —
`tests/assistant-quality/questions-basic.json`. Сегодня транспорт — запуск
клиента 1С с лончером; после подключения HTTP-сервисов к ИБ тот же контракт можно
дёргать HTTP-вызовом без перезапуска клиента.

**Лончер** — диагностическая обработка **внутри расширения**, вырезаемая при
сборке клиентской поставки (та же механика вырезаемых подсистем, что и у
редакций). Код обвязки живёт рядом с проверяемым кодом и использует
те же формы (стенд «Диагностика»); отдельный внешний артефакт не нужен.

Требования вырезания:

- граница вырезания накрывает **и обработку, и хук инициализации**; если хук
  оказывается вне границы — ссылки на обработку только косвенные (по имени
  строкой), чтобы сборка без неё не ломалась;
- префикс параметра запуска — свой (`prj_*`), чтобы не мешать штатному разбору
  параметров запуска БСП и параметрам хоста.

Запуск — без `/Execute`, только доп. параметром:

```
1cv8c ENTERPRISE /F "<путь к ИБ>" /C "prj_диагностика=<путь к сценарию>.json" /DisableStartupDialogs /DisableStartupMessages /Out "<лог>.txt"
```

Жизненный цикл:

1. Код инициализации сеанса (модуль приложения расширению недоступен — точка
   врезки: штатная обработка параметров запуска БСП в хосте, уточнить по
   хост-проекту) читает `ПараметрЗапуска`, распознаёт свой префикс и открывает
   форму диагностической обработки с путём к сценарию.
2. Форма: `ПриОткрытии` → `ПодключитьОбработчикОжидания(..., 0.1, Истина)` —
   не блокировать открытие, прогон стартует после отрисовки.
3. Выполнить сценарий согласно виду прогона (ассистент — через
   `prj_<Подсистема>КлиентСервер`: транспорт у вызывающего, лончер и есть
   вызывающий; схема/исполнитель — вызовы соответствующих обработок).
4. Записать файл результата **атомарно**: во временное имя, затем переименовать.
5. `ЗавершитьРаботуСистемы(Ложь)`.

Запасной вариант, если хук инициализации в хосте недоступен, — внешняя
обработка-лончер (`tools/`) через `/Execute "<лончер>.epf"`; жизненный цикл
внутри тот же, путь к сценарию — так же из `ПараметрЗапуска`.

Вызывающая сторона (сеанс Claude / скрипт):

- запускает процесс в фоне и ждёт **появления файла результата** с дедлайном;
- по истечении дедлайна убивает процесс;
- код возврата платформы не использует — истина только в файле результата.

## Чек-лист подводных камней лончера

1. **Асинхронность.** Если прогон асинхронный (Асинх/Ждать — например, петля
   ассистента) — завершать сеанс только после его реального конца; внутри
   лончера свой дедлайн (обработчик ожидания), иначе зависший HTTP-запрос
   даст вечно висящий клиент.
2. **Любой диалог = смерть прогона.** `/DisableStartupDialogs
   /DisableStartupMessages` обязательны; в коде прогона не должно быть
   `Вопрос`/`Предупреждение`; ошибки не глотать — писать в тот же файл
   результата (`{"ошибка": "..."}`) и завершаться.
3. **Пачки, а не одиночные запуски.** Старт клиента — секунды: сценарий
   принимает весь контрольный список и гоняет его за один сеанс.
4. **Прокси и ключи** живут в настройках ИБ и наследуются headless-сеансом,
   но системный прокси ОС платформа не подхватывает — проверять первым
   смоук-прогоном.
5. **Перед прогоном ИБ обновлена из проекта** (`update_infobase_status`) —
   иначе тестируется вчерашний код.
6. **Файловая ИБ и монопольность:** прогон — обычный сеанс, но обновление
   конфигурации ИБ требует, чтобы прогонов в этот момент не было.

## Сценарии — заготовки YAxUnit-тестов

Диагностический сценарий уже содержит половину теста: вход и ожидаемый
результат. Поэтому прогоны — не только проверка текущей задачи, но и разминка
перед полноценными тестами: граничные случаи, найденные в реальной работе,
не выдумываются задним числом.

При закрытии задачи, использовавшей headless-прогоны:

- **детерминированные** сценарии (вход → точное ожидание: функции ранжирования,
  построение схемы, рендеринг с эталоном) — кандидаты в YAxUnit; добавить
  пунктом в накопительный бэклог
  `tests/yaxunit-backlog.md`;
- **недетерминированные** (живой LLM) — в юниты не конвертируются, остаются
  регрессионным полигоном headless-прогонов.

Бэклог — файл в репозитории, а не issue: тестовые кандидаты не смешиваются с
задачами разработки в трекере. Задача в трекере появляется один раз — при
активации (триггеры — в самом файле), когда из бэклога нарезаются задачи на
реализацию тестов (`author_yaxunit_tests`).

## Где живут артефакты

| Артефакт | Место |
| --- | --- |
| Диагностическая обработка-лончер | в расширении, вырезается при сборке; запасной вариант — внешняя в `tools/` |
| Сценарии, контрольные наборы, README формата | `tests/<тема>/` (пример: `tests/assistant-quality/`) |
| Эталонные трассировки (для сравнения) | `tests/<тема>/`, коммитятся осознанно |
| Результаты разовых прогонов | временные каталоги, в репозиторий не попадают |
