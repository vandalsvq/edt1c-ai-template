# Навыки СКД и макетов (`skd-*`, `mxl-*`)

Девять навыков для работы со схемами компоновки данных и табличными документами через компактный
JSON DSL: анализ, генерация, точечная правка, валидация. Взяты из репозитория
[Nikolay-Shirokov/cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills) (лицензия MIT) и
адаптированы под EDT-проект.

- Забрано из коммита `bfef1b8` (2026-08-20), рантайм — Python.
- Текст лицензии апстрима — [`licenses/cc-1c-skills-LICENSE`](../licenses/cc-1c-skills-LICENSE).
- Не берётся: `epf-*`, `erf-*`, `cf-*`, `cfe-*`, `db-*`, `web-*`, `form-*`, `meta-*` и прочие группы
  апстрима. Часть из них дублирует codepilot1c, часть работает с конфигураторным форматом
  и противоречит нашим правилам (формы и метаданные — только через MCP).

## Состав

| Навык | Что делает |
| --- | --- |
| `skd-info` | Анализ схемы: наборы, поля, параметры, варианты; 11 режимов, включая трассировку происхождения поля |
| `skd-compile` | Генерация `Template.dcs` из JSON DSL |
| `skd-decompile` | `Template.dcs` → JSON-черновик в формате `skd-compile`. Из автоподбора моделью исключён (`disable-model-invocation`), вызывается явно |
| `skd-edit` | Точечная правка: 26 атомарных операций (add/set/patch/modify/clear/remove) |
| `skd-validate` | ~30 структурных проверок |
| `mxl-info` | Анализ макета: области, параметры, наборы колонок, объединения, рисунки |
| `mxl-compile` | Генерация `Template.mxlx` из JSON DSL |
| `mxl-decompile` | `Template.mxlx` → JSON-определение |
| `mxl-validate` | Структурные проверки макета |

## Установка

Единственная внешняя зависимость — `lxml`. Платформа 1С и EDT для работы навыков **не нужны**:
это чистая работа с XML, всё выполняется локально, в том числе на macOS.

```bash
pip3 install lxml
```

Если системный `pip` под запретом — завести venv и указывать его интерпретатор в вызовах:

```bash
python3 -m venv .venv && .venv/bin/pip install lxml
```

## Когда эти навыки, а когда MCP

| Задача | Чем |
| --- | --- |
| Создать макет как объект метаданных (uuid, имя, тип, регистрация у владельца) | Только MCP: `edt_validate_request` → `create_metadata` / `update_metadata`, либо EDT |
| Наборы данных, параметры, вычисляемые поля СКД — простые правки | `dcs_manage` (MCP) либо `skd-edit` — оба годятся |
| Варианты настроек СКД, группировки, выбранные поля, отборы, условное оформление | `skd-*`: `dcs_manage` этот слой не покрывает |
| Разобраться в чужой схеме, найти, откуда берётся поле | `skd-info` (`-Mode trace`) |
| Макет из пяти типовых секций, быстро | `render_template` (MCP) |
| Макет с именованными областями, объединениями, наборами колонок, рисунками | `mxl-*`: `render_template` умеет только фиксированные секции и шесть стилей |

## Нюансы EDT

Всё ниже проверено прогоном на реальных файлах EDT-проекта, а не взято из документации апстрима.

### 1. Имена файлов другие, содержимое то же

EDT кладёт схему компоновки в `<Объект>/Templates/<Имя>/Template.dcs`, а табличный документ —
в `<Объект>/Templates/<Имя>/Template.mxlx`. Конфигуратор оба зовёт `Template.xml`. **XML внутри
идентичен** (пространства имён `…/data-composition-system/schema` и `…/data/spreadsheet`), навыки
принимают путь параметром и ничего не хардкодят — работают по EDT-файлам как есть.

### 2. Сам макет навык не заводит

В EDT у макета **нет своего `.mdo`**. Он регистрируется блоком в `.mdo` объекта-владельца:

```xml
<templates uuid="d42a9ae3-37b5-4cf0-aad2-6de6a8ea485f">
  <name>ДанныеПечати</name>
  <synonym><key>ru</key><value>Данные печати</value></synonym>
  <templateType>DataCompositionSchema</templateType>
</templates>
```

Без `<templateType>` тип по умолчанию — табличный документ (`Template.mxlx`). Навыки пишут только
файл содержимого, поэтому порядок такой: **сначала завести макет через MCP или EDT, потом наполнять
навыком**. Файл, положенный в каталог мимо `.mdo` владельца, платформа не увидит.

### 3. Кодировка: правка внутри compile-скриптов

Апстрим пишет файл по конфигураторному соглашению — UTF-8 **с BOM** и переводами строк **CRLF**.
EDT держит `Template.dcs` и `Template.mxlx` без BOM и с LF, поэтому без вмешательства каждая
перекомпиляция давала бы дифф на весь файл (на реальном макете — +3.5 КБ пустой разницы).

**Правка внесена в сами скрипты**, отдельного шага нормализации нет. В `skd-compile.py` и
`mxl-compile.py` единственная точка записи — функция `write_edt_xml` (в апстриме `write_utf8_bom`),
помеченная комментарием `ЛОКАЛЬНАЯ ПРАВКА ШАБЛОНА`. Она сохраняет в UTF-8 без BOM и переводит
`CRLF`/`CR` в `LF`. Проверено: пересборка реального `Template.mxlx` даёт файл, совпадающий с
эталоном EDT, кроме четырёх строк со значениями по умолчанию (см. п. 4).

**`skd-edit` правки не требовал** — он правит на месте и кодировку сохраняет сам; точечная правка
реального `Template.dcs` дала дифф ровно в добавленных строках.

### 4. `*-decompile` → `*-compile` не идемпотентен

Круг «разобрать и собрать обратно» возвращает схему, близкую к исходной, но не байт-в-байт:

- у СКД пустой `<dcsset:settings/>` разворачивается в дерево настроек по умолчанию,
  `presentation` из простой строки становится `LocalStringType`, теряется `<value xsi:nil="true"/>`;
- у макета пропадают явно записанные `hidden`, `height`, `width`, `font`, совпадающие с умолчаниями.

Поэтому декомпиляция — инструмент **авторства нового по образцу** и структурной переработки, а не
способ «прогнать существующий макет туда-обратно». Автор апстрима исключил `skd-decompile` из
автоподбора моделью по той же причине.

### 5. Невалидный `-Value` не отвергается

`skd-edit` принимает компактный shorthand (`"Организация [Организация]: CatalogRef.Организации @hidden"`),
а не JSON. При неверном формате навык **не падает, а молча создаёт мусор**: JSON вместо shorthand
дал параметр с именем `{"name"` и типом `"ТестПараметр","type":"string"}`. Отсюда правило:

- работать только в чистом рабочем дереве (`git status --porcelain` пуст) — чтобы правку было видно;
- после каждой правки — `skd-validate` / `mxl-validate`, затем `edt_diagnostics`;
- смотреть `git diff` по файлу глазами, а не доверять сообщению `[OK]`.

### 6. `validation_token` не нужен

Это не MCP-инструменты, обязательный для мутаций codepilot1c контур `edt_validate_request` → токен
на них не распространяется. Но правило «после изменений — `edt_diagnostics`» действует: EDT должен
подтвердить, что макет читается.

## Обновление из апстрима

Апстрим версионирует скрипты в шапке файла (`# skd-compile v1.117`). Порядок сверки:

1. Склонировать [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills), сравнить версии в
   `.claude/skills/{skd,mxl}-*/scripts/*.py` с нашими.
2. Забрать обновлённые `*.py` (только Python-варианты, `*.ps1` мы не держим).
3. В `SKILL.md` при заборе повторить адаптацию: `powershell.exe … .ps1` → `python3 .claude/skills/<навык>/scripts/<скрипт>.py`,
   `Template.xml` → `Template.dcs` / `Template.mxlx`, сохранить шапку с атрибуцией и блоком «В EDT-проекте».
4. **В `skd-compile.py` и `mxl-compile.py` заново внести правку записи** — переименовать `write_utf8_bom`
   в `write_edt_xml`, сохранять в `utf-8` вместо `utf-8-sig` и заменять `\r\n` на `\n`. Функция и её
   единственный вызов помечены комментарием `ЛОКАЛЬНАЯ ПРАВКА ШАБЛОНА` — искать по нему.

Других расхождений с апстримом в скриптах нет: остальное — копия.

## Как отказаться

Если codepilot1c дорастёт до этих сценариев:

```bash
rm -rf .claude/skills/{skd,mxl}-* docs/skd-mxl-toolkit.md licenses/cc-1c-skills-LICENSE
```

плюс снять строки из `CLAUDE.md` → «Инструменты» и `README.md`. Отказ может быть частичным: слой
вариантов СКД и слой макетов закрываются независимо.
