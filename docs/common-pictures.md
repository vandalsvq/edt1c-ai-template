# Общие картинки (`CommonPicture`)

Как устроена общая картинка в EDT-проекте, что лежит в её манифесте, в каком порядке заводить
новую и как перенести готовую из поставки 1С (раздел 4).

> **Источники.** Раздел 2 сверен с «Руководством разработчика», глава 5, раздел 5.5.17
> «Общие картинки», редакции 8.3.18, 8.3.24, 8.3.27 и 8.5.1, и с манифестами живого
> расширения и БСП (около 370 архивов). В 8.3.24 и 8.3.27 раздел совпадает дословно. Что
> взято из практики, а не из документации, помечено *курсивом*.

## 1. Способы хранения

Картинка - папка `CommonPictures/<Имя>/` с `<Имя>.mdo` (имя, синонимы) и содержимым. Ссылки на
содержимое в `.mdo` нет: EDT находит его по имени файла. Способов хранения три:

| Способ | Где встречается | Для новых |
| --- | --- | --- |
| `Picture.png` - один растровый файл, без манифеста | старые иконки 16x16 | нет |
| `Picture.zip` с одним вариантом `l` и манифестом в одну строку | одиночные картинки, растр или SVG | нет |
| `Picture.zip` с вариантами плотности и `manifest.xml` | БСП и современные иконки | **да** |

## 2. Манифест

### 2.1. Набор вариантов

Общая картинка с манифестом - **набор вариантов**: zip-архив с файлами картинок и
манифестом, который говорит, какой файл для каких условий показа. Платформа сама выбирает
из набора вариант, ближайший к текущим условиям; от кода ничего не требуется. Условия
показа:

- **плотность экрана** (масштаб) - все версии;
- **вариант интерфейса** (Такси, 8.2, обычное приложение, 8.5) - все версии;
- **направление текста** (LTR / RTL) и **веб-браузер** - с 8.3.24;
- **тема** (светлая / тёмная) - с 8.5.1.

Обязателен вариант плотности `ldpi` - **базовая картинка**. Остальные необязательны: при
отсутствии нужного платформа берёт вариант с максимально близкими параметрами. Векторная
картинка кладётся тоже как `ldpi`; указывать для неё другие плотности, по документации 8.5.1,
смысла нет - она масштабируется сама. *На практике платформа отрисовывает SVG в его
собственном размере (`width` / `height`) и масштабирует уже растр: SVG 16px в варианте 150 %
выходит растянутым и размытым. Поэтому у каждой плотности свой файл со своим размером (3.2);
проверено 24.10.2026.*

В 8.5.1 документация говорит, что любая картинка хранится как набор вариантов, а обычный
файл - это набор из одного варианта `ldpi`. Выключить набор вариантов в конфигураторе 8.5
нельзя (в 8.3 была кнопка «Выключить набор вариантов» - оставляла только `ldpi` и снимала
шаблонность).

### 2.2. Файл манифеста

- Имя - `manifest.xml`, в 8.5.1 прямо сказано «обязательное имя файла». **Строго в нижнем
  регистре:** платформа регистр не различает, а EDT ищет манифест по точному имени. С
  `Manifest.xml` картинка в EDT пустая: без манифеста EDT строит варианты только по
  однобуквенным именам файлов (`l.*`, `m.*`, `h.*`, `x.*` - плотности ldpi, mdpi, hdpi, xdpi), а
  `100.svg` и прочие под это не подходят. *Выяснено по коду EDT 2026.1 (класс
  `ZipPictureContentStore`) 05.10.2026: в живом расширении 109 архивов из 143 были с
  `Manifest.xml` - в базе работали, в EDT не показывались.* Генератор иконок, если он есть в
  проекте, должен писать `manifest.xml`.
- XML в UTF-8. Корень `<Picture>`, внутри по одному `<PictureVariant/>` на вариант, без
  вложенных элементов. *Корневой элемент в опубликованной схеме не описан - только типы;
  взят из манифестов. Пространство имён в схеме 8.5.1 объявлено
  (`http://v8.1c.ru/8.1/data/core`), но ни в одном из проверенных манифестов расширения и БСП
  (369 архивов) `xmlns` нет - не указывать.*
- Имя файла варианта не регламентировано и служит только чтобы достать файл из архива;
  выбор варианта идёт по атрибутам. Один файл может стоять в нескольких вариантах.
  По схеме тип `name` - `xs:Name`, которому `100.svg` формально не соответствует (начинается
  с цифры); *платформа это не проверяет.*

### 2.3. Атрибуты `PictureVariant`

| Атрибут | С версии | Значения | Смысл |
| --- | --- | --- | --- |
| `name` | 8.3.18 | имя файла в архиве, **обязателен** | Файл варианта |
| `screenDensity` | 8.3.18 | см. 2.4, **обязателен** | Плотность экрана (масштаб), для которой вариант |
| `isTemplate` | 8.3.18 | `true` / `false`, по умолчанию `false` | Шаблонная картинка, см. 2.6 |
| `interfaceVariant` | 8.3.18, `version8_5` - 8.5.1 | см. 2.5; нет атрибута - «Любой» | Вариант интерфейса платформы |
| `glyphWidth`, `glyphHeight` | 8.3.18 | число, точки | **Размер ячейки коллекции** (не размер картинки), см. 2.7 |
| `direction` | 8.3.24 | `ltr`, `ltrCanFlipHorizontally`, `rtl`, `rtlCanFlipHorizontally`; нет атрибута - «Любое» | Направление текста, см. 2.8 |
| `webBrowser` | 8.3.24 | `MicrosoftInternetExplorerMicrosoftEdgeHTML` | Вариант только для указанного браузера в веб-клиенте; нужен в основном для SVG с анимацией |
| `glyphIndex` | 8.5.1 | число | Индекс элемента коллекции из векторных картинок, см. 2.7 |
| `theme` | 8.5.1 | `light`, `dark`; нет атрибута - «Любая» | Приоритетный вариант для светлой / тёмной темы. Без темы вариант берётся, когда для текущей темы нет своего |

В редакции 8.3.24 атрибут `direction` в тексте назван `PictureDirectionVariant`, в 8.5.1 -
`directionVariant`: это опечатки документации, в самой схеме атрибут - `direction`. Атрибут
`theme` в схеме 8.5.1 пропущен (объявлен только тип `Theme`), но описан в диалоге набора
вариантов и встречается в манифестах. *`theme=""` равнозначно отсутствию атрибута - «Любая»;
выведено из примеров.*

**Совместимость.** Проект в режиме совместимости 8.3 может держать в манифестах значения 8.5
(`version8_5`, `theme`). *Старая платформа такие варианты не выбирает, но архив грузит* -
проверено на расширении в режиме 8.3.18 с полутора сотнями вариантов `version8_5`. Поэтому
варианты для 8.5 добавлять можно, но базовый `ldpi` без `interfaceVariant` и `theme`
обязан быть: только его увидит 8.3.

### 2.4. Плотность экрана (`screenDensity`)

| Значение | Масштаб | Мобильные устройства | Растр при базе 16 точек |
| --- | --- | --- | --- |
| `bldpi` | 85 % | | 14 |
| `ldpi` | 100 % - базовая | менее 140 dpi | 16 |
| `aldpi` | 125 % | | 20 |
| `mdpi` | 150 % | 140-180 dpi | 24 |
| `amdpi` | 175 % | | 28 |
| `hdpi` | 200 % | 180-270 dpi | 32 |
| `xdpi` | 300 % | более 270 dpi | 48 |
| `udpi` | 400 % | | 64 |

Размер растра для каждой плотности - размер базовой картинки, умноженный на масштаб.

Рекомендуемый размер **растровой** картинки при 100 %:

- пиктограмма (меню, панель, табличный документ) - не более 16x16;
- картинка в табличном поле - не более 14x14;
- кнопка выбора поля ввода - не более 9x9;
- представление подсистемы - не более 48x48.

Если картинка используется в нескольких местах - ориентироваться на меньший размер.

### 2.5. Вариант интерфейса (`interfaceVariant`)

| Значение | Интерфейс | Задаётся в конфигураторе |
| --- | --- | --- |
| нет атрибута | Любой | да |
| `version8_5` | Версия 8.5 (с 8.5.1) | да |
| `taxi` | Такси | да |
| `taxiCompact` | Такси, компактный режим | только правкой манифеста |
| `taxiMobile` | Такси, мобильное приложение | да |
| `version8_2` | Версия 8.2 | да |
| `version8_2_OrdinaryApp` | Обычное приложение | только правкой манифеста |
| `version8_0` | Конфигурации 8.0 / 8.1 | в 8.3 - только правкой манифеста |

### 2.6. Шаблонная картинка (`isTemplate`)

Шаблонная картинка несёт изображение только в альфа-канале: цветовые каналы должны давать
белый (R=G=B=255). При показе фон поля заливается текущим цветом фона, а непрозрачные
точки рисуются текущим цветом текста с интенсивностью по альфе - картинка сама окрашивается
под оформление формы и тему. Цветная картинка (`isTemplate="false"`) - та, где цвет несёт
смысл (например, флаги).

Формат шаблонной картинки: в 8.3 рекомендован PNG 32 бита, в 8.5.1 - **SVG**. *У SVG
с `isTemplate="true"` заливка `#000000` работает: платформа берёт только прозрачность.*

### 2.7. Коллекция картинок (`glyphWidth`, `glyphHeight`, `glyphIndex`)

Коллекция - картинка, из которой элемент выбирается по индексу во время исполнения
(например, картинка строки списка). Два способа:

- **растровая коллекция** (все версии): одна картинка-матрица из ячеек одного размера.
  `glyphWidth` / `glyphHeight` - размер ячейки; ширина картинки кратна ширине ячейки,
  высота - высоте. Нумерация слева направо, сверху вниз. Пример: картинка 468x26 при ячейке
  26x26 - 18 элементов;
- **векторная коллекция** (8.5.1, рекомендованный способ): несколько SVG-вариантов `ldpi`,
  у каждого свой `glyphIndex`.

Выбор элемента в 8.5: сначала по `glyphIndex`; если индекс 0 или такого нет - по размеру
ячейки, если `glyphWidth` / `glyphHeight` не нулевые; иначе они игнорируются. Коллекция без
индекса показывает элемент с индексом 0, при его отсутствии - с минимальным.

Для картинки, которая **не коллекция**, `glyphWidth` / `glyphHeight` не нужны. *В манифестах
БСП они стоят почти везде и равны размеру картинки для своей плотности (16 при `ldpi`) - то
есть описывают «коллекцию из одного элемента». Образец из 2.11 их содержит и работает; при
копировании образца не трогать, в новом ручном манифесте для одиночной SVG можно не писать.*

### 2.8. Направление (`direction`)

| Значение | Представление | LTR-интерфейс | RTL-интерфейс |
| --- | --- | --- | --- |
| нет атрибута | Любое | как есть | как есть |
| `ltrCanFlipHorizontally` | Слева направо, можно переворачивать | как есть | зеркально |
| `rtlCanFlipHorizontally` | Справа налево, можно переворачивать | зеркально | как есть |
| `ltr` | Слева направо | приоритетный вариант | как есть |
| `rtl` | Справа налево | как есть | приоритетный вариант |

Порядок выбора между вариантами с разным направлением:

- LTR: `ltr` → `ltrCanFlipHorizontally` → `rtlCanFlipHorizontally` → Любое → `rtl`;
- RTL: `rtl` → `rtlCanFlipHorizontally` → `ltrCanFlipHorizontally` → Любое → `ltr`.

Если проекту RTL не нужен - атрибут не ставить.

### 2.9. Форматы и ограничения SVG

Поддерживаются BMP, GIF, JPEG, PNG, TIFF, ICO, SVG, WMF, EMF. Для GIF - только расширения
NETSCAPE2.0, ANIMEXTS1.0 и XMP DataXMP. Для пиктограмм 8.5.1 рекомендует SVG, при
невозможности - растр без потерь (PNG, GIF). Прозрачный цвет в конфигураторе задаётся
только для BMP, JPEG, TIFF.

В SVG платформа **игнорирует**:

- JavaScript и интерактивность, включая CSS вроде `:hover` (скрипты клиент вырезает);
- свойства стиля `color-interpolation`, `color-rendering`, `enable-background`;
- маркеры у пути нулевой длины;
- фильтр-примитив `feTile`;
- встроенные шрифты: `font`, `altGlyph`, `altGlyphDef`, `altGlyphItem`, `glyphRef`;
- ссылки на внешние ресурсы; относительный путь в `image` не поддерживается.

Отсюда для своих рисунков: только геометрия (`path`, фигуры), без текста шрифтом, скриптов и
внешних ссылок.

### 2.10. Схема манифеста (8.5.1)

Официальная схема, в том виде как опубликована (атрибута `theme` в ней нет, см. 2.3):

```xml
<xs:schema targetNamespace="http://v8.1c.ru/8.1/data/core"
	xmlns:tns="http://v8.1c.ru/8.1/data/core" xmlns:xs="http://www.w3.org/2001/XMLSchema"
	elementFormDefault="qualified">
	<xs:complexType name="PictureVariant">
		<xs:attribute name="name" type="xs:Name" use="required"/>
		<xs:attribute name="screenDensity" type="tns:PictureVariantScreenDensity" use="required"/>
		<xs:attribute name="interfaceVariant" type="tns:PictureInterfaceVariant"/>
		<xs:attribute name="direction" type="tns:PictureDirectionVariant"/>
		<xs:attribute name="webBrowser" type="tns:WebBrowser"/>
		<xs:attribute name="isTemplate" type="xs:boolean" default="false"/>
		<xs:attribute name="glyphIndex" type="xs:decimal"/>
		<xs:attribute name="glyphWidth" type="xs:decimal"/>
		<xs:attribute name="glyphHeight" type="xs:decimal"/>
	</xs:complexType>
	<!-- перечисления: PictureVariantScreenDensity (2.4), PictureInterfaceVariant (2.5),
	     Theme (light, dark), PictureDirectionVariant (2.8),
	     WebBrowser (MicrosoftInternetExplorerMicrosoftEdgeHTML) -->
</xs:schema>
```

В 8.3.18 в схеме только `name`, `screenDensity`, `isTemplate`, `interfaceVariant`,
`glyphWidth`, `glyphHeight`; 8.3.24 добавляет `direction` и `webBrowser`; 8.5.1 -
`glyphIndex`, значение `version8_5` и тип `Theme`.

### 2.11. Образец манифеста

```xml
<?xml version="1.0" encoding="utf-8"?>
<Picture>
	<PictureVariant name="85.svg" screenDensity="bldpi" isTemplate="true" glyphWidth="14" glyphHeight="14"/>
	<PictureVariant name="100.svg" screenDensity="ldpi" isTemplate="true" glyphWidth="16" glyphHeight="16"/>
	<PictureVariant name="125.svg" screenDensity="aldpi" isTemplate="true" glyphWidth="20" glyphHeight="20"/>
	<PictureVariant name="150.svg" screenDensity="mdpi" isTemplate="true" glyphWidth="24" glyphHeight="24"/>
	<PictureVariant name="175.svg" screenDensity="amdpi" isTemplate="true" glyphWidth="28" glyphHeight="28"/>
	<PictureVariant name="200.svg" screenDensity="hdpi" isTemplate="true" glyphWidth="32" glyphHeight="32"/>
	<PictureVariant name="300.svg" screenDensity="xdpi" isTemplate="true" glyphWidth="48" glyphHeight="48"/>
	<PictureVariant name="400.svg" screenDensity="udpi" isTemplate="true" glyphWidth="64" glyphHeight="64"/>
	<PictureVariant name="150.svg" screenDensity="mdpi" interfaceVariant="version8_5" isTemplate="true" glyphWidth="24" glyphHeight="24"/>
</Picture>
```

Восемь плотностей - восемь файлов: рисунок один, а `width` / `height` у каждого свой - размер
`ldpi`, умноженный на масштаб (2.4): 14, 16, 20, 24, 28, 32, 48, 64 для иконки 16px (2.1, 3.2).
По документации 8.5.1 вектору хватило бы одного `ldpi`; *полный набор плотностей - формат, в
котором картинки хранит БСП, и в нём проверена вставка в табличный документ (3.3) - поэтому
новые делаются по образцу целиком.* Последняя строка - вариант для интерфейса 8.5. Удобно
держать в проекте одну картинку в этом формате как эталон и собирать новые из её манифеста
(3.3).

**Вариантов для интерфейса 8.2 и обычного приложения** (`version8_2`,
`version8_2_OrdinaryApp`) не заводить, если проект не работает в этих интерфейсах; у старых
картинок они снимаются (3.7). Образцы БСП их ещё содержат - для новых не копировать.

## 3. Порядок создания

### 3.1. Объект - через MCP

`create_metadata` (`kind=CommonPicture`, имя с префиксом `prj_`), затем `update_metadata`
с синонимом на языках конфигурации. В `Configuration.mdo` EDT сам добавит `<content>`
и `<commonPictures>`. Объект создаётся без содержимого.

### 3.2. Рисунок

SVG рисовать самим, не брать со сторонних ресурсов: у чужой картинки нужно выяснять
лицензию. `viewBox="0 0 24 24"`, `width="16px" height="16px"`, цвет `#000000` - с
`isTemplate="true"` цвет задаёт платформа (2.6). Только геометрия, без того, что платформа в
SVG игнорирует (2.9). *Обводка (`stroke`) в шаблонной картинке работает так же, как
заливка.*

Размер в `width` / `height` - собственный размер картинки: его возвращают `Картинка.Ширина()` /
`Высота()` и по нему EDT рисует превью. Для иконки он 16px при `ldpi`, даже если картинку потом
вставляют в табличный документ крупно: размер рисунка задаёт код вставки (3.3), а не картинка.
В файлах остальных плотностей размер умножается на масштаб (2.11), рисунок и `viewBox` те же -
это делает сборка архива (3.3). *Одинаковый 16px во всех восьми файлах даёт размытую
картинку на масштабе больше 100 % (2.1).*

Иконки интерфейса - только SVG; PNG для новых не заводится. Монохромная иконка - одна
шаблонная картинка, цветная - варианты по теме (`theme`, 2.3). Если в проекте есть набор
дизайн-материалов, прежде чем рисовать, посмотреть его: подходящая иконка оттуда оформляется
в проект этим же порядком. Окончательную визуальную доводку иконки делает владелец в
редакторе - достаточно отдать чистый вектор в стиле соседних.

Заимствованные иконки (например, производные от VS Code codicons, CC BY 4.0) записываются с
источником и лицензией: обязательство лицензии остаётся и проверяется при аудите поставки.

### 3.3. Архив

`Picture.zip` по образцу (2.11): один рисунок в восьми файлах плотностей, у каждого свой
`width` / `height` (3.2); содержимое манифеста - копия образца байт в байт, имя файла -
`manifest.xml` (2.2).

```bash
python - <<'EOF'
import re, zipfile
src = "<Каталог.Имя>/src/CommonPictures"
with zipfile.ZipFile(f"{src}/prj_Эталон/Picture.zip") as z:   # картинка-образец (2.11)
    manifest = z.read("manifest.xml")
svg = open("картинка.svg", encoding="utf-8").read()   # свой рисунок, width="16px" height="16px"
base = 16                                              # размер при ldpi
with zipfile.ZipFile(f"{src}/prj_Имя/Picture.zip", "w", zipfile.ZIP_DEFLATED) as z:
    for scale in (85, 100, 125, 150, 175, 200, 300, 400):
        size = round(base * scale / 100)
        variant = re.sub(f'width="{base}px"', f'width="{size}px"', svg, count=1)
        variant = re.sub(f'height="{base}px"', f'height="{size}px"', variant, count=1)
        z.writestr(f"{scale}.svg", variant)
    z.writestr("manifest.xml", manifest)
EOF
```

Проверка после сборки: `width` в `85.svg` и `400.svg` - 14px и 64px.

Картинка в таком формате годится и для вставки в табличный документ. Размер рисунка при
вставке задаёт код, который вставляет картинку; без явного размера берётся собственный размер
картинки (3.2).

### 3.4. Подсистема

Если состав поставки задают подсистемы, картинку включить в ту же подсистему, что и её
потребителя: строка `<content>CommonPicture.prj_Имя</content>` в mdo подсистемы. Состав
подсистемы MCP не правит (`update_metadata` запрещает `subsystems`), строка дописывается
руками.

### 3.5. Картинка команды формы

`mutate_form_model` / `add_command` картинку команды как дизайнер не ставит (параметр
`picture` даёт SU113, см. [`codepilot1c-reference.md`](codepilot1c-reference.md), «Командные
панели»), `set.tooltip` игнорирует: команда создаётся только с заголовком. Картинку и подсказку дописать в `Form.form` по образцу
соседней команды (`<toolTip>`, `<use>`, `<picture xsi:type="core:PictureRef">`). Заготовку
обработчика инструмент кладёт в конец модуля, вне областей: перенести к соседним
обработчикам.

Мутация формы через MCP пересохраняет `Form.form` из модели EDT **целиком**: если модель
разошлась с диском, чужие свойства молча откатываются (так слетал `<visible>false</visible>`
у группы формы). После каждой мутации - `git diff` формы на строки, не относящиеся к задаче.

### 3.6. Проверка

- `get_diagnostics` по форме и модулю - ноль ошибок и предупреждений;
- в базе глазами: картинка на кнопке, в том числе при масштабе 150 % или 200 % - не размыта;
  если картинка вставляется в табличный документ - размер вставленного рисунка.

### 3.7. Долг старых картинок

Правила 2.11 и 3.2 старые картинки часто нарушают; приводить их по мере правки картинки или
отдельной задачей, без смены рисунка. Список картинок-должников удобно держать в проектном
документе со счётом на дату.

- **Варианты `version8_2` / `version8_2_OrdinaryApp` в манифесте - снять**, если проект не
  работает в этих интерфейсах. Если файл, на который ссылался снятый вариант, больше нигде не
  стоит (`Picture.png` растровых картинок), - удалить и его из архива.
- **Одинаковый размер SVG на всех плотностях - разнести по 3.3.** У картинок, которые
  вставляются в табличный документ, после правки сверить размер вставленного рисунка (3.3).
- **Коллекции** - масштабирует ли платформа ячейку коллекции так же, как одиночную картинку,
  не проверено: сначала опыт на одной (4.5).

Искать картинки с вектором по содержимому (`<svg`), а не по расширению `.svg`: вектор бывает
и в файле без расширения (`l`).

## 4. Перенос картинки из поставки 1С (БСП, СППР)

Картинки БСП в проекте обычно лежат копиями: имя с префиксом `prj_`, содержимое - из
конфигурации, из которой копировали. В новых редакциях 1С дорисовала к растру вектор, поэтому
к перенесённой однажды картинке возвращаются за векторной версией. Разобрано 18.10.2026 на
СППР 2.1 (платформа 8.5): 763 общие картинки, у 713 внутри есть SVG.

### 4.1. Выгрузка картинок из файловой базы

`ibcmd` выгружает выбранные объекты, целиком конфигурацию гонять не нужно. База не должна быть
занята конфигуратором или агентом EDT - иначе «Ошибка блокировки информационной базы для
конфигурирования» (обход - выгрузка с клона файла базы, [`codepilot1c-reference.md`](codepilot1c-reference.md)).

```bash
IBCMD="<путь к ibcmd нужной версии платформы>"
БАЗА="<каталог файловой базы-источника>"
# 1. корень конфигурации - оттуда список имён
$IBCMD config export objects --db-path="$БАЗА" --user=Администратор -o /tmp/корень Configuration
grep -o "<CommonPicture>[^<]*</CommonPicture>" /tmp/корень/Configuration.xml | sed 's/<[^>]*>//g' > /tmp/имена.txt
# 2. сами картинки (каталог -o должен быть пустым, иначе отказ)
args=(); while IFS= read -r n; do args+=("CommonPicture.$n"); done < /tmp/имена.txt
$IBCMD config export objects --db-path="$БАЗА" --user=Администратор -o /tmp/картинки "${args[@]}"
```

Выгрузка - в формате конфигуратора, а не EDT: `CommonPictures/<Имя>.xml` плюс
`CommonPictures/<Имя>/Ext/Picture/Picture.zip`. Архив внутри - тот же, что в EDT-проекте.

### 4.2. Какая картинка чьей копией является

**Сопоставлять по содержимому, а не по имени.** Хэши файлов внутри архивов находят пару
надёжно: картинка проекта может совпасть с `Успешно32` (32x32), а не с одноимённой `Успешно`
(16x16) - перенос по имени подменил бы размер иконки. Имя - только подсказка, подтверждение -
совпадение растровых вариантов байт в байт.

### 4.3. Что лежит в архиве поставки

- растровые плотности `85.png` … `400.png` плюс `Picture.png` для интерфейса 8.2;
- **моно-вектор** - `<дата>-<номер>.svg` с `isTemplate="true"` и `interfaceVariant="version8_5"`;
- **цветной вектор** - `Picture.svg`, базовый `ldpi` без `interfaceVariant`;
- у части картинок вместо одного вектора пара с `theme="light"` и `theme="dark"`.

Вектор поставки виден только на интерфейсе 8.5: в её манифесте у SVG стоит
`interfaceVariant="version8_5"`. Если проект живёт и на 8.3 (режим совместимости, «Такси»),
манифест переносимой **иконки** пересобирается по 3.3 - SVG на все плотности без
`interfaceVariant`, тогда вектор работает и на «Такси».

**Картинки дерева метаданных - кандидат на исключение: архив поставки копируется байт в байт.**
У них 1С держит обе версии - цветную (`Picture.svg`, базовый `ldpi`) и монохромную для
интерфейса 8.5: на 8.3 и «Такси» иконка цветная, на 8.5 монохромная. Своего в архиве ничего
нет, поэтому и обёртка, и манифест остаются как в поставке; у четырёх картинок
(`МетаданныеПланыВидовХарактеристик`, `МетаданныеРегистрыНакопления`, `МетаданныеРесурсы`,
`МетаданныеЯзыки`) цветного вектора у 1С нет, его место занимает растровый `Picture.png`.
Разнобой здесь дороже, чем в одиночных иконках: дерево метаданных показывает их рядом, и
картинка, пересобранная по 3.3, среди соседей выделяется монохромной на 8.3. Выбранный формат
держать одинаковым на весь набор `prj_Метаданные*`; новая картинка метаданных заводится копией
архива поставки.

### 4.4. Порядок переноса

0. Картинка дерева метаданных, если проект принял исключение 4.3, - скопировать `Picture.zip`
   поставки целиком и на этом закончить. Шаги ниже - про иконки.
1. Взять нужный вариант: моно - по `isTemplate="true"`, цветной - по `theme="light"` либо
   единственный без темы; у цветных предпочесть вариант с `interfaceVariant="version8_5"` -
   `Picture.svg` рядом с ним бывает старым рисунком другого размера.
2. Переоформить обёртку по 3.2: свой пролог, `viewBox` источника без изменений, собственный
   размер в `width` / `height` - тот, что был у растра при `ldpi` (16 для иконки, 32 для
   картинок `*32`).
3. Собрать `Picture.zip` по 3.3 - размер в каждой плотности от базы шага 2 (`base` в
   скрипте). Тёмный вариант, если он есть, кладётся теми же восемью плотностями под именами
   `85d.svg` … `400d.svg`, в манифесте - с `theme="dark"`; базовый `ldpi` остаётся без `theme`
   (2.3).
4. Прежнее содержимое каталога удалить: при переходе с `Picture.png` на `Picture.zip` файл
   `Picture.png` в каталоге не оставлять.
5. Синонимы в `.mdo` не меняются - переносится только содержимое.

### 4.5. Коллекция картинок

В поставке коллекция - матрица: растр с ячейкой 16 точек и SVG с ячейкой 24
(`КоллекцияПиктограммФайлов` - 78 элементов, `viewBox="0 0 1872 24"`). Ячейку задаёт не
`viewBox`, а собственный размер картинки, поэтому при переносе он приводится к сетке проекта:
`width` = 16 × число элементов, `height` = 16, `viewBox` - как в источнике. Тогда
`glyphWidth` / `glyphHeight` остаются прежними (14 / 16 / 20 / 24 / 28 / 32 / 48 / 64 по
плотностям) и индексы элементов в коде не сдвигаются. Это размер `ldpi`; разносить ли его по
плотностям, как у одиночной картинки (3.2), - не проверено (3.7).

Перед переносом сверить число элементов: ширина растра `100.png`, поделённая на 16, должна
совпасть с шириной `viewBox`, поделённой на ячейку SVG. Не совпало - в поставке добавили или
убрали элементы, и обращения по индексу поедут.

Манифест коллекции - единственное место, где 3.3 не копируется байт в байт: `glyph`-атрибуты
нужны (2.7), а у картинки, которая не коллекция, их наоборот быть не должно.
