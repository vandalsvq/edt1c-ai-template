# Развёртывание YAxUnit + METR на новом проекте - playbook

Пошаговый порядок поднятия headless-тестовой среды для расширения 1С с нуля,
написанный **по следам реального развёртывания** (~месяц календарного
времени, из которых бо́льшая часть ушла на две ошибки диагностики). Цель документа -
чтобы повторное развёртывание заняло часы, а не недели.

Здесь только переносимое: значения конкретного стенда (пути, версии, имена баз)
заводите в своей проектной памятке. Смежный документ - [`testability.md`](testability.md)
(headless-лончер для недетерминированных прогонов; он **дополняет** юниты, а не
заменяет).

## 0. Как этим пользоваться

Разделы 1-6 читать подряд при развёртывании, командами из §9 - исполнять.
Раздел 7 («Каталог грабель») - справочник, к которому возвращаются, когда что-то
не работает: он организован по **симптомам**, а не по причинам, потому что в
момент поломки виден именно симптом. Раздел 8 - про метод диагностики; его стоит
прочесть **до** начала, он дороже всего остального. §10 - чем закрывать работу.

Документ самодостаточен: за командами никуда уходить не нужно.

## 1. Что получается на выходе

- Тесты живут в репозитории как исходники EDT и собираются в тестовую ИБ
  автоматически.
- Агент гоняет их одним вызовом MCP-инструмента и читает структурированный отчёт.
- В разработке агент после правки гоняет модули затронутых объектов прямо в рабочей
  базе, одной командой и без закрытия IDE (§6.1).
- Есть независимый резервный путь прогона на случай, когда MCP-сервер недоступен.

## 2. Предпосылки

| Компонент | Требование | Комментарий |
| --- | --- | --- |
| Платформа 1С | 8.3.10+ | нужен `ibcmd` (идёт в комплекте) |
| 1С:EDT | 2025.1+ | нужен `1cedtcli` |
| JDK | 17+ | берётся из комплекта EDT, отдельно ставить не нужно |
| YAxUnit | 25.12+ | `.cfe` из релиза |
| METR (`mcp-onec-test-runner`) | v0.5.2+ | готовый JAR из релиза, собирать из исходников не нужно |
| ОС | практически проверено на Windows; прогон в рабочей базе (§6.1) - и на macOS | на других ОС отличаются пути и поведение с кодировками |

## 3. Развилки, которые надо пройти до начала

**Где живут тесты.** Варианты: внутри расширения YAxUnit / в основном расширении /
**в отдельном собственном расширении**. Рекомендация - отдельное расширение:
движок обновляется заменой `.cfe` независимо, тесты не попадают в дистрибутив,
основное расширение не трогается вообще.

> Плата за это решение: объекты, добавленные **другим** расширением, не видны
> на этапе компиляции. Обращаться к ним придётся динамически -
> `Обработки["ИмяОбработки"].Создать()` вместо `Обработки.ИмяОбработки`.
> Это компилируется всегда и разрешается в рантайме.

**Какая инфобаза.** Для сборки через METR и полного прогона - только выделенная тестовая,
не база разработки: прогон грузит исходники в подключённую ИБ и меняет данные. Модули
затронутых объектов в разработке гоняются и в рабочей базе - её обновляет сама EDT, а модули,
пишущие данные, туда не пускаются (§6.1).

**Как её наполнить.** Не строить с нуля - засеять снимком (`DumpIB`/`RestoreIB`)
рабочей базы. Первичная реструктуризация крупной конфигурации в пустой файловой
базе идёт **часами**; на снимке те же шаги - секунды. Снимок сохранить: пересев
базы из него занимает ~минуту и это главный способ отката.

**Кто собирает.** `builder: IBCMD` - headless, для агента. `DESIGNER` - для
локальной работы человека.

## 4. Порядок развёртывания

1. **Тестовая ИБ.** Создать пустую файловую базу, восстановить в неё снимок
   рабочей. Запомнить пользователя и пароль из снимка - они понадобятся везде.
2. **Движок YAxUnit.** Загрузить `.cfe` в ИБ как расширение, снять «Безопасный
   режим» и «Защиту от опасных действий». EDT-проект движка **не нужен**.
3. **EDT-проект тестового расширения.** Создать расширение конфигурации.
   Требования к имени - см. §5, они неочевидны и ломают всё молча.
4. **Проверить `Configuration.mdo` на `containedObjects`.** Если их нет, `1cedtcli`
   выгрузит XML без узла `InternalInfo`, и `ibcmd config import` откажет
   («Отсутствует внутренняя информация»). Лечится добавлением узлов
   `<containedObjects classId=… objectId=…/>` (одинаковые `classId`, свои `objectId`).
5. **Конфиг METR** (`application-*.yml`): `format: EDT`, `base-path` - общий предок
   деревьев исходников (пути в `source-set` не должны содержать `..`),
   `source-set` с **обязательной** записью `type: CONFIGURATION` на исходники
   хост-конфигурации, плюс `EXTENSION`-записи. `name` каждой записи = имя EDT-проекта
   в воркспейсе.
6. **Конфиг MCP-клиента**: запуск `java -jar <METR jar>`, путь к yml через env
   `SPRING_CONFIG_IMPORT`, каталог `1cedtcli.exe` в env `PATH`.
7. **Смоук:** самый дешёвый инструмент (`check_syntax_edt`), затем прогон.
8. **Машинно-локальные конфиги - в gitignore**, в репозиторий только `*.example`
   с плейсхолдерами. Они содержат абсолютные пути, строки подключения и версии
   платформы - на другой машине всё это неверно.

## 5. Устройство тестового расширения (жёсткие требования)

**Имя расширения - без точки.** YAxUnit адресует тестовый модуль как
`<ИмяРасширения>.<ИмяМодуля>`. Точка делает идентификатор неоднозначным, и модуль
**молча** выпадает из обнаружения: ни ошибки, ни предупреждения - просто ноль тестов.
Ловушка усиливается тем, что METR регистрирует расширение в базе под именем
**EDT-проекта**, а не под именем конфигурации расширения, причём в обход валидации
`ibcmd` (сам `ibcmd extension create` точку запрещает). То есть достаточно назвать
EDT-проект `Foo.Tests` - и тесты не найдутся, хотя внутри всё правильно.

**Имя - латиницей.** Кириллица в имени EDT-проекта ломает `1cedtcli`
(«no matches found»). Имена объектов **внутри** расширения кириллицей - нормально.

**Префикс имён.** Расширение имеет `namePrefix`, и платформа требует, чтобы с него
начиналось **каждое** имя объекта. Готовая схема именования из документации YAxUnit
(`ОМ_<Объект>`, `Обр_<Объект>_МО`) поэтому неприменима как есть - префикс типа
переезжает внутрь: `<Префикс>Тест<Объект>`.

**Структура для обнаружения** - оба условия обязательны:

1. Тестовый модуль - **клиентский** общий модуль: `ClientManagedApplication=true`,
   `ClientOrdinaryApplication=true`, `Server=false`, `ServerCall=false`,
   `Global=false`. Серверные модули с `ИсполняемыеСценарии` игнорируются молча.
2. Модуль включён в подсистему вида `<Префикс>ЮТПодключаемыеМодули` → дочернюю
   подсистему → в её `Content`.

**Серверная часть - отдельным модулем** с `ServerCall=true`, и его **не** включать
в подсистему: там только клиентские модули с тестами. Наружу такой модуль отдаёт
сериализуемые значения (структуры, примитивы).

**Назначение расширения** - `add-on`, как у движка YAxUnit. METR создаёт расширение
как `customization`, игнорируя `<configurationExtensionPurpose>` из исходника.
Задаётся только при создании (`ibcmd extension create --purpose=add-on`); у
`extension update` ключа `--purpose` нет, поменять можно лишь пересозданием.

## 6. Пути прогона

**В рабочей базе** - основной путь агента в разработке: после правки гоняются модули
затронутых объектов в той же базе, где идёт разработка, без METR и без закрытия IDE (§6.1).
Полный прогон и модули, которые пишут данные, остаются за выделенной тестовой базой - одним из
двух путей ниже.

**Через MCP** - основной для тестовой базы: один вызов делает инкрементальную сборку и
прогон, возвращает структурированный отчёт.

**Напрямую платформой** - резервный, но более предсказуемый; не требует ни
MCP-сервера, ни перезапусков после правки конфигов. Полный цикл - в §9.

Резервный путь стоит поднять сразу, а не «когда понадобится»: именно он спасает,
когда MCP-сервер держит протухший кэш конфига или дерётся за воркспейс.

### 6.1. Прогон в рабочей базе

Базу обновляет сама запущенная EDT по команде codepilot1c, тесты запускает клиент ключом
`/C RunUnitTests` с отбором модулей. Цикл «правка → прогон модуля» - десятки секунд.

```text
правка → пауза → update_infobase (codepilot1c) → проверка свежести → 1cv8c /C RunUnitTests → вердикт по файлам
```

**Однократная подготовка.**

- Проект тестового расширения лежит в воркспейсе EDT рядом с основным и привязан к рабочей
  базе: при обновлении EDT возит его в базу вместе с основным расширением.
- **Движок EDT не возит.** `YAXUNIT` - отдельное расширение, его проекта в воркспейсе нет;
  ставится в базу один раз из `.cfe`. Признак, что движок на месте, - меню «YAxUnit» в клиенте.
- У движка и тестового расширения сняты безопасный режим и защита от опасных действий.
  Снимается один раз: EDT и платформа это свойство сами не меняют. Пока EDT подключена к
  файловой базе, `ibcmd` получает «Ошибка блокировки информационной базы для
  конфигурирования» - ставить движок и снимать флаги через интерфейс платформы.
- Без движка или с ним в безопасном режиме клиент **молча закрывается** через минуту-полторы с
  кодом 0 - ни отчёта, ни лога YAxUnit. Выглядит как «прогон не запустился».

**Шаг 1. Обновление базы** - `edt_diagnostics(command="update_infobase",
project_name="<ХостПроект>")`: в воркспейсе расширения это проект хост-конфигурации, к которому
привязана база. Ответ `UPDATE_FAILED` бывает ложным, а ответ клиента MCP «session expired» не
значит, что вызов не дошёл до EDT. Итог - только по логу EDT `<воркспейс>/.metadata/.log`,
записи после строки со своим `op_id`.

**Не ставить `update_infobase` в один пакет вызовов с правкой файлов** и не звать его сразу
следом. EDT грузит в базу то, что успела заметить к моменту вызова, а файл, записанный мимо неё
(скриптом, `sed`, `edit_file`), замечает с задержкой. Порядок - правка → пауза (полминуты) →
`update_infobase`. Грузить по изменениям или целиком, EDT решает сама: полная загрузка
как средство не нужна, а на большой конфигурации она занимает час и больше.

**Шаг 2. Свежесть кода в базе - две проверки.**

1. **Незакоммиченные правки - по логу EDT.** После своего `op_id` должна быть строка
   `Загрузка N объектов конфигурации в информационную базу ...`. Правок не было - строки не
   будет, это норма. Правки были, а строки нет - пауза и повтор. Ни число N, ни время строки
   правку не подтверждают: загрузка могла увезти правки, замеченные раньше. Сомнение снимает
   ещё один обычный `update_infobase`: загрузил что-то - предыдущий был неполным; строки
   загрузки нет - база совпадает с тем, что видит EDT. Замер (проверено 10.10.2026): обновление
   через 2 с после правки прошло вхолостую, и прогон дал **ложный зелёный** на сломанном
   утверждении; повтор через 25-45 с правку довёз.
2. **База в целом - по версии.** Лог YAxUnit в начале перечисляет расширения базы с версией и
   безопасным режимом. Версия основного расширения должна совпадать с `version` в его
   `Configuration.mdo`: так ловится база, отставшая на коммит или залитая из другой ветки.
   Незакоммиченные правки версию не меняют - их ловит только проверка 1.

Что именно лежит в базе, а не в модели EDT, показывает выгрузка объектов из базы - справочник
codepilot1c, «Обновление сразу после правки мимо EDT».

**Шаг 3. Прогон** - как в §9, с тремя отличиями: база - рабочая; в `run.json` отбор модулей
затронутых объектов; у клиента дедлайн, без него зависший клиент висит вечно:

```powershell
filter = @{ extensions = @($PROJ); modules = @('prj_ТестОбъект') }   # в $cfg из §9

$t0 = Get-Date
$p = Start-Process -FilePath "$BIN\1cv8c.exe" -ArgumentList $a -PassThru
if (-not $p.WaitForExit(300000)) { Stop-Process -Id $p.Id -Force }
```

**Шаг 4. Вердикт - по файлам, не по коду процесса.** Клиент выходит с кодом 0 и на красном
прогоне. Результат - `exitcode.txt` (0 - всё прошло, 1 - есть падения) **и** `report.xml`
свежее момента старта; отчёта нет или он старый - прогон не состоялся (см. «молча
закрывается»). Текст падения - в атрибуте `message` элемента `failure`, стек до строки
тестового модуля - в его тексте.

**Ограничения.**

- Только модули затронутых объектов. Модули, которые пишут в базу и прибирают за собой
  вручную, без транзакции, в рабочей базе не гонять: упавший посередине или снятый по дедлайну
  тест оставит мусор в данных разработки. Их место - тестовая база, пока они не переведены на
  `ВТранзакции()` YAxUnit. Новый тест, пишущий данные, - сразу в транзакции.
- Полный прогон тестового расширения - в тестовой базе и в CI, не здесь.
- Клиент теста - лишнее подключение к базе; лицензия разработчика число клиентов ограничивает.

**macOS** (проверено 10.10.2026). Путь тот же, отличия:

- пути в `run.json` - обычные, через `/`; кириллица в аргументах проходит обычным массивом
  shell, обход из §9 - виндовый;
- пустой пароль - без `/P`: иначе платформа берёт паролем следующий ключ;
- `timeout` в macOS нет - дедлайн держит скрипт прогона;
- `exitcode.txt` пишется с BOM: `[ "$(cat exitcode.txt)" = 0 ]` ложно и на зелёном прогоне -
  читать с `utf-8-sig` либо считать падения по отчёту;
- нативной компоненты YAxUnit под macOS в старых сборках движка нет: тест, который упал только
  на маке, проверить и на этот счёт;
- **лимит клиентов.** Запуски считает агент конфигуратора, которым EDT обновляет базу
  (`1cv8 DESIGNER /F<база> /AgentMode`), и клиент, закрытый до конца прогона, в этом счётчике
  остаётся - и снятый по дедлайну, и завершившийся по просьбе. После двух-трёх таких запусков -
  отказ «Превышено ограничение лицензии для разработчиков на количество клиентов
  информационной базы», и сам он не проходит. Лечение - завершить процесс агента своей базы;
  EDT поднимает его при следующем `update_infobase`, обновление идёт штатно. Агента не снимать,
  пока EDT обновляет базу.

**Скрипт прогона.** Шаги 2-4 стоит свести в скрипт проекта: на вход - модули или отбор по диффу
ветки, на выходе код 0 - все прошли, 1 - есть красные, 2 - стенд (прогона не было или его
результату нельзя верить), последняя строка - вердикт с причиной. Базу перед ним обновляет
агент: `update_infobase` - инструмент MCP. Скрипт сам:

- сравнивает время последней строки «Загрузка N объектов» в логе EDT с самым свежим файлом
  исходников: файл новее - код 2 без прогона, так ловится ложный зелёный;
- пишет `run.json`, держит дедлайн, выносит вердикт по файлам;
- сверяет версию основного расширения и безопасный режим по логу YAxUnit;
- пропускает и называет модули, пишущие данные (их список - константой в скрипте; только
  сокращается);
- при отборе по диффу берёт модуль, если он или его серверная пара обращается к затронутому
  объекту по имени, а затронутые объекты без такого модуля выводит строкой «не покрыты».
  Косвенное покрытие так не видно - это повод проверить, а не обязательно дыра.

Команда скрипта записывается в CLAUDE.md, раздел «Тестирование»: на неё ссылается цикл этапа
([`stage-cycle.md`](stage-cycle.md), раздел 7).

## 7. Каталог грабель (по симптомам)

| Симптом | Причина | Лечение |
| --- | --- | --- |
| Тесты не обнаруживаются, ошибок нет, ноль тестов | Точка в имени расширения (§5) | Переименовать EDT-проект в имя без точки |
| То же, но имя чистое | Модуль серверный, либо не включён в подсистему `*ЮТПодключаемыеМодули` → дочернюю | Проверить флаги модуля и `Content` подсистемы |
| Прогон висит бесконечно, процесс жив, но CPU почти не растёт | `ibcmd config apply` без `--force` печатает интерактивный запрос «Принять изменения [y/n]» и ждёт ввода, которого в headless не будет | Снять процесс, выполнить `config apply --force` вручную. Возникает при **структурных** изменениях; правка только кода модулей их не вызывает |
| «Пользователь ИБ не идентифицирован» | Кириллическое имя пользователя разрушается при проходе через **командную строку шелла** | Передавать аргументы **массивом**: `Start-Process -ArgumentList @(...)`. Кириллица тут ни при чём - виноват транспорт (см. §8) |
| «EDT cli не запущено, попробуйте позже» | Осиротевший `1cedtcli` держит воркспейс; новый умирает на занятом lock'е | Снять все `1cedtcli`, сервер поднимет свой. В логе сервера - «Процесс завершился во время чтения данных» |
| То же после обновления EDT | Каталог компонента сменился, путь в env `PATH` протух | Поправить путь и **перезапустить MCP-сервер** |
| Правка конфига не действует | MCP-сервер читает конфиг и env **на старте** | Перезапустить сервер; либо идти резервным путём (§6) |
| `config import` ругается «Отсутствует внутренняя информация» | В `Configuration.mdo` нет `containedObjects` → экспорт без `InternalInfo` | Добавить узлы (§4.4) |
| Синтакс-проверка «успешно», но код не работает | Агрегированный статус инструмента может скрывать «Ошибка конфигурации» | Читать файл лога проверки, а не только статус |
| Сборка каждый раз полная, `safe-mode` сбрасывается | Кэш хешей METR на Windows не сохраняется (`mapdb VolumeIOError`) → расширение переимпортируется каждый прогон | Снимать `safe-mode` после каждого импорта; смириться либо обновить METR |
| Пустая ИБ собирается часами | Первичная реструктуризация крупной конфигурации | Засеять базу снимком (§3) |
| Тест в чужом расширении не компилируется | Объекты другого расширения не видны на компиляции | Динамическое обращение `Обработки["Имя"]` |

## 8. Метод диагностики - то, что стоило месяца

Четыре ошибки в **способе** искать, каждая из которых удлинила работу сильнее,
чем любая техническая проблема.

**Сначала выяснить, что инструмент уже логирует.** Ответ на главный вопрос
(«почему тесты не обнаруживаются») лежал в отладочном логе YAxUnit, который
пишется при каждом прогоне и содержит и список расширений глазами рантайма, и
поимённую загрузку сценариев. Вместо этого строились обходные маршруты - поднять
отладчик, посмотреть в GUI, снять трейс. Прежде чем добывать новое наблюдение,
проверить, не собирается ли оно уже само.

**Сравнивать эталон со своим объектом на всех слоях.** Рабочий пример (демо-тесты
движка) и наш сломанный сравнивались только по XML метаданных - там всё совпадало
байт-в-байт, и это укрепляло тупик. Расхождение было слоем ниже: в **регистрации
расширения в базе**. Слоёв обычно четыре - исходник в репозитории, результат
экспорта, регистрация в базе, представление в рантайме, - и сравнивать надо все,
а не тот, который удобнее смотреть.

**Барьер локализовать точнее, чем «X не работает».** Вывод «кириллица в аргументах
не проходит, прямой запуск клиента недоступен» закрыл целый маршрут диагностики на
месяц. На деле не проходила кириллица **через командную строку шелла**, а через
массив аргументов проходила прекрасно. Формулировка «не работает X» почти всегда
шире правды; сузив её, часто находишь работающий обход.

**Не доверять агрегированному «успешно».** Проверка синтаксиса рапортовала
`success: true` с пустым списком проблем, а в её же файле лога лежали ошибки
конфигурации. Зелёный агрегат - повод открыть артефакт, а не повод расслабиться.

**И общее:** симптом «молча ничего не произошло» почти никогда не означает, что
проверять нечего. Он означает, что объект отсеялся раньше того места, куда мы
смотрим - и искать надо выше по конвейеру, а не глубже в том же месте.

## 9. Готовые команды

Windows/PowerShell. Подставить свои значения в переменные первого блока - дальше
всё копируется как есть. На другой ОС меняются пути к исполняемым файлам; приём
с `Start-Process` актуален именно для Windows.

```powershell
# --- значения стенда ---------------------------------------------------------
$V     = '8.3.27.2214'                        # версия платформы
$EDT   = 'C:\Program Files\1C\1CE\components\1c-edt-2026.1.3+25-x86_64'
$BIN   = "C:\Program Files\1cv8\$V\bin"
$WS    = 'D:/EDT/my_ws'                       # воркспейс EDT
$PROJ  = 'Tests'                              # имя EDT-проекта = имя расширения, БЕЗ ТОЧКИ
$DB    = 'D:\1C DB\my_test'                   # тестовая ИБ
$USER  = 'Администратор'                      # кириллица допустима, см. приём ниже
$PWD   = ''
$WORK  = 'C:\Temp\yax'                        # рабочий каталог (короткий путь)

New-Item -ItemType Directory -Path $WORK -Force | Out-Null
$ib = @("--db-path=$DB", "--user=$USER", "--password=$PWD")
```

**Засев тестовой ИБ снимком** (вместо сборки с нуля, §3):

```powershell
# дамп рабочей базы; /S для серверной, /F для файловой
Start-Process -FilePath "$BIN\1cv8.exe" -Wait -PassThru -ArgumentList @(
  'DESIGNER','/S "сервер\рабочая_иб"',"/N`"$USER`"","/P`"$PWD`"",
  '/DumpIB',"`"$WORK\snapshot.dt`"",'/DisableStartupDialogs','/DisableStartupMessages')
# восстановление в тестовую
Start-Process -FilePath "$BIN\1cv8.exe" -Wait -PassThru -ArgumentList @(
  'DESIGNER',"/F`"$DB`"","/N`"$USER`"","/P`"$PWD`"",
  '/RestoreIB',"`"$WORK\snapshot.dt`"",'/DisableStartupDialogs','/DisableStartupMessages')
```

**Создание тестового расширения в базе** (имя без точки, назначение `add-on`):

```powershell
& "$BIN\ibcmd.exe" infobase config extension create @ib `
    --name=$PROJ --name-prefix=prj_ --purpose=add-on
```

**Цикл «правка → прогон»** - это и есть рабочая петля:

```powershell
# 1. EDT -> XML. Воркспейс должен быть СВОБОДЕН
Get-Process -Name 1cedtcli -ErrorAction SilentlyContinue | Stop-Process -Force
$xml = "$WORK\xml"
if (Test-Path $xml) { Remove-Item $xml -Recurse -Force }
New-Item -ItemType Directory -Path $xml -Force | Out-Null
& "$EDT\1cedtcli.exe" -data $WS -command export --project-name $PROJ --configuration-files $xml

# 2. XML -> база. --force ОБЯЗАТЕЛЕН, иначе вечное зависание на запросе [y/n]
& "$BIN\ibcmd.exe" infobase config import @ib --extension=$PROJ $xml
& "$BIN\ibcmd.exe" infobase config apply  @ib --extension=$PROJ --force
& "$BIN\ibcmd.exe" infobase config extension update @ib --name=$PROJ `
    --safe-mode=no --unsafe-action-protection=no

# 3. Прогон. Аргументы МАССИВОМ - иначе кириллица в $USER разрушится
$a = @('ENTERPRISE',"/F`"$DB`"","/N`"$USER`"","/P`"$PWD`"",
       '/C',"RunUnitTests=$WORK\run.json",'/Out',"$WORK\ent.log",
       '/DisableStartupDialogs','/DisableStartupMessages')
$p = Start-Process -FilePath "$BIN\1cv8c.exe" -ArgumentList $a -Wait -PassThru
"exit=$($p.ExitCode)"

# 4. Результат
([xml](Get-Content "$WORK\report.xml" -Encoding UTF8)).testsuites.testsuite |
    Select-Object name,tests,failures,errors | Format-Table -AutoSize
```

`run.json` (UTF-8 **без BOM** - иначе платформа не разберёт):

```powershell
$cfg = @{
  filter       = @{ extensions = @($PROJ) }   # убрать filter = гонять всё
  reportFormat = 'jUnit'
  reportPath   = "$WORK\report.xml"
  exitCode     = "$WORK\exitcode.txt"
  closeAfterTests = $true
  showReport      = $false
  logging      = @{ file = "$WORK\yax.log"; console = $false; level = 'debug' }
} | ConvertTo-Json -Depth 5
[System.IO.File]::WriteAllText("$WORK\run.json", $cfg, (New-Object System.Text.UTF8Encoding($false)))
```

**Диагностика.** `$WORK\yax.log` - главный артефакт (§8): список расширений глазами
рантайма и поимённая загрузка сценариев. Проверка компиляции расширения отдельно:

```powershell
Start-Process -FilePath "$BIN\1cv8.exe" -Wait -PassThru -ArgumentList @(
  'DESIGNER',"/F`"$DB`"","/N`"$USER`"","/P`"$PWD`"",
  '/CheckModules','-Extension',$PROJ,'/Out',"$WORK\check.log",
  '/DisableStartupDialogs','/DisableStartupMessages')
Get-Content "$WORK\check.log" -Encoding Default
```

**Состояние расширений в базе** - первое, что смотреть при «тесты не находятся»:

```powershell
& "$BIN\ibcmd.exe" infobase config extension list @ib
# здоровое: name без точки, purpose: add-on, safe-mode: no, hash-sum не из одних A
```

**Снять зависший прогон** (процесс живёт, CPU не растёт):

```powershell
Get-Process -Name ibcmd -ErrorAction SilentlyContinue | Stop-Process -Force
& "$BIN\ibcmd.exe" infobase config apply @ib --force     # добить вручную
```
