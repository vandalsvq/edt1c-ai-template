# Промпт первичной инициализации проекта

Этот документ - пошаговая инструкция для **Codex и Claude Code**, как настроить новый проект, созданный из шаблона `edt1c-ai-template`. Используется один раз сразу после клонирования.

## Подготовка пользователя (до запуска агента)

Перед запуском промпта выполните три действия вручную:

1. **Склонируйте шаблон в свой проект.**

   ```bash
   cp -r edt1c_ai_template my-project
   cd my-project
   rm -rf .git && git init
   ```

   Или используйте «Use this template» на GitHub, затем `git clone <url>`.

2. **Создайте EDT-проект** в корне репозитория (без этого промпт остановится - проект нужен, чтобы автоматически вытащить имя, префикс и платформу):

   - В EDT: `File → New → 1C:Enterprise project`.
   - Имя проекта на латинице: `<Каталог>.<НазваниеПроекта>` (например, `MyCompany.MyProject`).
   - Префикс объектов: например, `prj_`.
   - Тип: `Configuration` (новая конфигурация) / `Configuration extension` (расширение) / `Library` (библиотека).
   - Версия платформы 1С - желаемая.
   - Расположение каталога - корень репозитория (рядом с `PROJECT.md`).

   После создания в репозитории появится каталог `<Каталог>.<НазваниеПроекта>/src/Configuration/Configuration.mdo` (или аналогичный для расширения/библиотеки).

3. **Запустите Codex или Claude Code** в корне репозитория и дайте задачу:

   > Выполни инструкцию из `docs/project-init.md`.

---

## Алгоритм для агента (выполнять последовательно)

> **Идемпотентность.** Промпт можно запускать повторно (например, после добавления EDT-проекта позже или при смене состава). Перед каждым изменением файла - прочитай текущее состояние и спроси пользователя: пропустить / обновить / переделать. Не перезаписывай уже заполненные значения без подтверждения.
>
> **Тон.** Все вопросы и сообщения - на русском языке.

### Шаг 0. Предварительные проверки

1. Убедись, что текущий каталог - git-репозиторий (`git status`). Если нет - попроси пользователя выполнить `git init` и вернуться.
2. **Проверь историю git.** Если последний коммит - это коммит шаблона (`init: шаблон репозитория для разработки 1С в EDT с Claude Code` или ему подобный, проверь `git log -1 --format=%s`), значит репозиторий получен через `git clone` шаблона и унаследовал его историю. Спроси пользователя:
   - **Чистая история** (рекомендуется для нового проекта) - выполни `rm -rf .git && git init && git branch -m main` (или `master`, по выбранной релизной ветке на Шаге 1). Это деструктивное действие - попроси явное подтверждение.
   - **Сохранить историю шаблона** - оставь как есть; пользователь дальше сам решает, ребейзить или нет.
3. Найди EDT-проект: ищи каталоги, где `src/Configuration/Configuration.mdo` или `src/ConfigurationExtension/ConfigurationExtension.mdo` или `src/<...>.mdo` (используй `Glob`/`Bash`).
4. **Если EDT-проект не найден - остановись.** Покажи пользователю инструкцию из раздела «Подготовка пользователя» (пункт 2) и попроси создать проект через EDT, затем запустить промпт повторно. Дальше не двигайся.
5. Если найдено несколько EDT-проектов - спроси, какой основной (он попадёт в раздел «Проект» PROJECT.md), какие - host/extension/library (они попадут в таблицу «EDT-воркспейс»).

### Шаг 1. Сбор данных о проекте

Извлеки автоматически из EDT-проекта:

- **Каталог EDT-проекта** - имя найденного каталога.
- **Имя проекта (латиницей)** - из имени каталога или из `Configuration.mdo` (атрибут `name`).
- **Тип проекта** - по структуре: `Configuration` / `ConfigurationExtension` / `Library`.
- **Версия платформы 1С** - из `Configuration.mdo` (атрибут `compatibilityMode` / `version`).
- **Текущая версия конфигурации** - из `Configuration.mdo` (атрибут `version`).
- **Префикс объектов** - попробуй определить по именам существующих объектов в `Catalogs/`, `CommonModules/`, `Subsystems/` (общий префикс перед `_`). Если префикса нет или объекты ещё не созданы - спроси.

Спроси у пользователя одной серией вопросов (используй `AskUserQuestion`):

- **Краткое описание проекта** - одно предложение для PROJECT.md и README.md.
- **URL трекера задач** - например, GitHub Issues, Jira, Linear, или «нет трекера».
- **Релизная ветка** - default `main` (если ветка `main` уже создана в репо) или `master`.
- **Ветка разработки** - default `develop`. Если разработка ведётся прямо в релизной ветке - спроси и зафиксируй.
- **Формат имени feature-ветки** - default `feature/<prefix>-<N>`.
- **Формат коммита** - default «короткий заголовок `<prefix>-<N> <что сделано>; <версия>`, в теле первой строкой `<URL issue>`, дальше подробности» (PROJECT.md, «Ветки и коммиты»).
- **Соглашение об инкременте версии** - оставить пример из шаблона или предложить своё.
- **Схема репозиториев** - один репозиторий или пара «публичный + приватный» с разными префиксами задач. Если один - раздел «Трекер задач и репозитории» в PROJECT.md сокращается до строки в разделе «Проект».
- **Публичная витрина** - есть ли публичный репозиторий, сайт или changelog. Если нет - подраздел «Публичные формулировки» из PROJECT.md удаляется.
- **Команды трекера** - как посмотреть задачу и как оставить комментарий (для GitHub: `gh issue view` / `gh issue comment`). Нужны скиллу `close-task`; если трекера нет - так и записать.
- **История релизов** - путь к файлу changelog, если он ведётся, или «нет».
- **Передача на функциональное тестирование** - есть ли в процессе аналитик или тестировщик, которому задача уходит на проверку. Если есть - нужен ли ему PDF на печать (колонка «Отметка» под галочку) или достаточно Markdown в каталоге спеки. Нужно скиллу `analyst-doc`; если такой передачи нет - так и записать.
- **Способы проверки** - какие механизмы в проекте есть или будут подключены: YAxUnit, Vanessa Automation, headless-лончер, функциональное тестирование (предыдущий вопрос). Диагностика и отладчик MCP зависят от MCP-сервера EDT - уточняются на Шаге 4. Ответ идёт в `PROJECT.md` → «Тестирование»: шаблон спеки выбирает способ проверки только из этого перечня ([`testability.md`](testability.md) → «Доступность ступеней»).
- **Цвета в формах** - «стилевые» (default: элементы стиля, цвета палитры 8.5, `WebЦвета` и абсолютные цвета запрещены) или «значения» (`WebЦвета` и абсолютные разрешены). «Значения» нужны решению, которое ставится на произвольную конфигурацию - например, универсальному расширению: нужных элементов стиля в чужой конфигурации может не быть. Ответ идёт в `PROJECT.md` → «Соглашения по коду», строка «Цвета в формах», и в настройку `tools/form-audit/form-audit.py` (Шаг 5.Д).
- **Разработка на macOS** - работает ли кто-то в EDT на macOS. Нужно скиллу `close-task`: при «нет» проверка мак-сочетаний клавиш пропускается.

Сохрани все ответы в плоскую структуру в памяти (в виде таблицы) - она понадобится на следующих шагах.

### Шаг 2. Заполнить `PROJECT.md`

1. Прочитай `PROJECT.md`.
2. **Удали блок-предупреждение** в начале:

   ```markdown
   > Это **шаблон**. Перед началом работы заполните разделы со знаком `<...>` под свой проект и удалите этот блок-предупреждение.
   ```

3. Замени плейсхолдеры (`<...>`) собранными данными в следующих разделах:
   - **«Проект»** - имя, описание, каталог EDT-проекта, префикс, платформа, трекер.
   - **«EDT-воркспейс»** - таблица заполняется только если EDT-проектов больше одного. Иначе оставь раздел с одной строкой или удали таблицу и оставь короткую заметку.
   - **«Соглашения по коду»** - префикс уже подставится в строку про новые объекты; в строке «Цвета в формах» оставь выбранное значение (ответ из Шага 1), «Зону владельца» заполни или убери опциональную часть.
   - **«Трекер задач и репозитории»** - заполни таблицу, если репозиториев два; если один - удали раздел целиком, оставив строку «Трекер задач» в разделе «Проект». Подраздел «Публичные формулировки» оставь только при наличии публичной витрины.
   - **«Ветки и коммиты»** - релизная и dev-ветки, формат feature-ветки, формат коммита, соглашение об инкременте версии. Путь к `Configuration.mdo` обнови под фактический. Строку «Версия модуля обработки» заполни или удали.
   - **«Структура»** - приведи дерево каталогов под фактическое имя EDT-проекта (или нескольких).
   - **«Тестирование»** - строка «Доступные способы проверки» по ответу из Шага 1; описания неподключённых механизмов оставь с пометкой «не подключён». Если на Шаге 4 подключение MCP-сервера отложат - убери из перечня диагностику и отладчик MCP.
   - **«Синхронизация документации»** - таблица заполняется под проект; если синхронизировать пока нечего, оставь один пример-строку с пометкой «заполняется по мере роста проекта».
4. **Не трогай** разделы с пустыми таблицами «Ключевые подсистемы / Обработки / Общие модули / Роли» - оставь как есть, с инструкцией пользователю заполнить их по мере появления (можно добавить TODO-заметку «заполняется по мере роста проекта»).
5. Сохрани файл.

### Шаг 3. Адаптировать `README.md`

Текущий `README.md` - это README шаблона. Спроси у пользователя:

- **Сгенерировать новый README с нуля** под проект (заголовок, описание, ссылки на AGENTS.md / CLAUDE.md / PROJECT.md / specs / docs, краткая инструкция «как разрабатывать»), или
- **Оставить текущий и адаптировать** (поменять заголовок и описание, остальное оставить как есть).

Сделай выбранное. В обоих случаях:

- Замени заголовок и описание на данные проекта.
- Удали раздел «Источник» про PrintWizard, если пользователь явно не попросит сохранить.
- Удали разделы «Как использовать» (шаги 1-7 шаблона) - они больше не актуальны.
- Раздел «Благодарности и смежные проекты» - предложи **сохранить**: это атрибуция сторонних проектов, а не описание шаблона. Ссылка на `hbk_md` актуальна, пока в проекте подключён skill `bsl-check`.
- Раздел «Обновление проектов из шаблона» оставь: скиллы `sync-template` / `push-to-template` в проекте работают.

### Шаг 4. MCP-сервер

Выбор сервера - по версии EDT проекта (спроси, если не ясно из Шага 1):

- **EDT 2026.1 и новее - EDT-MCP** (основной сервер шаблона, имя `edtmcp`). `PROJECT.md` уже
  написан под него: в разделе «Инструменты» строка «MCP-сервер» - `EDT-MCP`.
- **EDT старше 2026.1 - codepilot1c**: EDT-MCP такие версии не поддерживает. Раздел «Инструменты»
  в `PROJECT.md` замени текстом из [`codepilot1c-reference.md`](codepilot1c-reference.md),
  «Раздел для PROJECT.md» (подзаголовки навыков `bsl-check`, `skd-*` и следующие оставь);
  в `.mcp.json.example` имя сервера - `codepilot1c`, порт по умолчанию 8765.

Проверь выбранный сервер в текущем клиенте. Для Codex выполни `codex mcp list`. Для Claude Code:

```bash
claude mcp list 2>/dev/null | grep -iE 'edtmcp|codepilot1c'
```

- **Если найден** - сообщи, какой сервер подключён, замерь один вызов диагностики объекта
  (EDT-MCP - `get_project_errors` с `projectName` и `objectFqns=[<любой объект проекта>]`;
  codepilot1c - `get_diagnostics` с `project_name`, `scope=project`, `object`) и заполни
  параметр «Диагностика пачкой» в `PROJECT.md` (раздел «Инструменты»): секунды и меньше - «да»,
  десятки секунд - «нет»; время и дату замера - туда же. Затем переходи к Шагу 5.
- **Если не найден** - спроси у пользователя:
  - **Подключить сейчас.** EDT-MCP: в EDT «Справка → Установить новое ПО», сайт
    `https://ditrixnew.github.io/EDT-MCP/`, пакет **EDT MCP Server Feature**, перезапуск EDT;
    порт - «Настройки → MCP Server → Server Port», уровень согласия - **Allow all**
    ([`edt-mcp-reference.md`](edt-mcp-reference.md) §1; там же лечение, если плагин после
    установки не поднялся). codepilot1c: `Help → Install New Software`, update site
    `https://ondysss.github.io/codepilot1c-edt/`, пакет «1C Copilot», сервер слушает
    `http://127.0.0.1:8765/mcp`. В Codex зарегистрировать сервер командой `codex mcp add <имя-сервера> --url http://127.0.0.1:<порт>/mcp`. В Claude Code скопировать `.mcp.json.example` в `.mcp.json` и
    подставить порт, либо `claude mcp add --transport http -s local <edtmcp|codepilot1c> http://127.0.0.1:<порт>/mcp`.
    Дождись подтверждения и проверь повторно.
  - **Отложить.** Сообщи: «Можно подключить позже командой подключения выбранного клиента. Без MCP-сервера
    инструменты типизации, метаданных, форм и СКД будут недоступны - справочник в
    `docs/edt-mcp-reference.md` (или `docs/codepilot1c-reference.md`)».

### Шаг 5. Skill `bsl-check`

При отказе от опционального навыка в шагах ниже убирай также одноимённый вход из `.agents/skills/`, чтобы Codex предлагал только установленные процедуры.

Спроси у пользователя одно из трёх:

- **Подключить сейчас** (skill будет работать после настройки).
- **Отложить** (оставить файлы как есть, настроить позже руками по `docs/bsl-check-setup.md`).
- **Не нужен** (удалить skill из шаблона целиком).

#### 5.A. «Подключить сейчас»

Действуй по `docs/bsl-check-setup.md`, выполняя шаги от имени пользователя:

1. **Найти `hbk_md`.** Спроси путь или предложи default `~/Repository/hbk_md`. Проверь, существует ли каталог.
   - **Не существует** - спроси разрешения и склонируй: `git clone https://github.com/vandalsvq/hbk_md.git <path>`. Это сетевая операция, требующая подтверждения.
   - **Существует, но без `.claude/1c-syntax-check.py`** - каталог занят чем-то другим. Спроси другой путь.
2. **Проверить готовый справочник.** Найди `<hbk_md>/shcntx_ru_v*/search-index-ru.json`.
   - **Найден** - справочник готов, переходи к шагу 5.A.4.
   - **Не найден** - нужно разобрать `.hbk`. Перейди к шагу 5.A.3.
3. **Разобрать `.hbk`.**
   - Спроси у пользователя путь к файлу справочника `*.hbk` (обычно `shcntx_ru.hbk` из дистрибутива платформы или с диска ИТС).
   - Спроси версию платформы в формате `X.X.X.X` (например, `8.5.1.1302`) - чтобы переименовать `.hbk` под convention утилиты.
   - Скопируй файл: `cp <user-path> <hbk_md>/<X.X.X.X>.hbk`.
   - Запусти разбор: `cd <hbk_md> && python3 process_hbk_complete.py`. Это может занять несколько минут.
   - Проверь, что появился `<hbk_md>/shcntx_ru_v<X.X.X.X>/search-index-ru.json`. Если нет - покажи вывод утилиты и сообщи об ошибке, дальше не двигайся.
4. **Задать путь для клиента.** В Codex передай `HBK_MD_HOME` в окружение команды проверки по шагу 3 руководства `docs/bsl-check-setup.md` и переходи к пункту 5. В Claude Code задай путь в `.claude/settings.local.json`. `SKILL.md` редактировать не надо - он берёт каталог из переменной `HBK_MD_HOME`. Если `settings.local.json` ещё нет - скопируй из `.example` (см. Шаг 6 ниже). Затем:
   - В секции `env` подставь абсолютный путь к каталогу `<hbk_md>`:

     ```json
     "env": { "HBK_MD_HOME": "<abs-path-to-hbk_md>", "PYTHONIOENCODING": "utf-8" }
     ```

   - В `permissions.allow` убедись, что есть две строки (в `.example` они уже добавлены, не дублируй):

     ```json
     "Bash(: \"${HBK_MD_HOME:?*)",
     "Bash(python3 \"$HBK_MD_HOME/.claude/1c-syntax-check.py\":*)"
     ```

5. **Проверить.** Вызови навык в выбранном клиенте с аргументом `Структура.Вставить`. Для проверки самого справочника запусти `python3 <abs-path-to-hbk_md>/.claude/1c-syntax-check.py Структура.Вставить`. Должно вернуть `✓ Структура.Вставить (Structure.Insert)`. Если нет - покажи вывод и продиагностируй (раздел Troubleshooting в `docs/bsl-check-setup.md`).

#### 5.B. «Отложить»

Не трогай файлы skill. Сообщи: «Skill зарегистрирован, но не настроен. Когда будете готовы - пройдите `docs/bsl-check-setup.md`».

#### 5.C. «Не нужен»

Удали:

- каталог `.claude/skills/bsl-check/`,
- документ `docs/bsl-check-setup.md`,
- упоминания skill `bsl-check` в `PROJECT.md` (раздел «Skill `bsl-check`», строку про «Сомнения в API…» в разделе «Инструменты»),
- упоминания в `README.md` (шаг про подключение skill, строку в дереве «Что внутри», если она там осталась).

### Шаг 5.Б. Настройка skill `close-task`

Заполни таблицу «Настройка под проект» в `.claude/skills/close-task/SKILL.md` ответами из Шага 1: трекер, префиксы задач и репозитории, ветка разработки, каталог EDT-проекта, команды просмотра и комментирования задачи, путь к истории релизов, наличие метода `Версия()` у обработок, разработка в EDT на macOS.

Если трекера нет - в строке «Трекер задач» так и напиши `нет`, а строки «Просмотр задачи» / «Комментарий к задаче» заполни значением `нет`: скилл эти шаги пропустит и будет работать по номеру из имени ветки.

### Шаг 5.В. Навыки `skd-*` и `mxl-*`

Спроси, нужны ли навыки для схем компоновки и табличных документов (`docs/skd-mxl-toolkit.md`):

- **Нужны** - проверь `python3 -c "import lxml"`. Если модуля нет, подскажи `pip3 install lxml` (или venv) и напомни, что платформа 1С этим навыкам не требуется.

### Шаг 5.Д. Скрипты `tools/`

### Шаг 5.Е. Лицензия шаблона и правила участия

`LICENSE` и `CONTRIBUTING.md` в корне - файлы самого шаблона, а не проекта:

- `CONTRIBUTING.md` - удали (`git rm CONTRIBUTING.md`): это правила участия в шаблоне. Из вводного абзаца `AGENTS.md` убери обе фразы о работе в самом шаблоне вместе со ссылкой на этот файл.
- `LICENSE` - перенеси в `licenses/edt1c-ai-template-LICENSE` (`git mv LICENSE licenses/edt1c-ai-template-LICENSE`). MIT требует сохранять уведомление об авторских правах в копиях: файлы, пришедшие из шаблона, остаются под ним, а код проекта под ним не оказывается.
- Своя лицензия проекта в корне - спроси пользователя: положить его `LICENSE` (тогда добавить его в первый коммит, шаг 9) или обойтись без него (обычно для закрытого репозитория).

## Что делать, если промпт прерван посередине

Промпт идемпотентен. Запусти его повторно - он определит текущее состояние:

- Уже заполненный PROJECT.md (нет `<...>` плейсхолдеров) - спросит, нужно ли менять, или пропустит.
- Для Codex повторно проверь навык из рабочего дерева. В Claude Code skill уже подключён (в `.claude/settings.local.json` есть `env.HBK_MD_HOME` и оба permission-правила) - спросит, нужно ли переподключать.
- Если после прерывания ты не уверен в состоянии - спрашивай у пользователя, не действуй наугад.
